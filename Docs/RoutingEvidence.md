# What a routing rule can observe

Only evidence available before an egress decision can choose where the first packet goes. A rule may also inspect evidence that arrives later and decide to continue or end the flow. This document describes the shipping capture paths and the additional mechanisms required for name- and application-aware routing. The companion design defines rule evaluation, connection tracking and related flows. [Routing language](RoutingLanguage.md)

## Evidence at each capture point

| Capture point | Available evidence | Limits |
| --- | --- | --- |
| Ordinary destination-routed packet tunnel | IP version, source and destination addresses, protocol, ports when present, ingress and member generation known to the engine | The virtual router reads raw packets. On macOS, even a switch to `readPacketObjects` supplies `NEPacket.metadata` only for a tunnel configured with source-application routing. |
| DNS proxy | DNS question name, type, class, original resolver endpoint, reply bytes and flow metadata | A question describes a lookup. A resolver daemon, shared cache, prefetch, or app's own resolver can break the relationship to a subsequent socket. Several lookups can share a flow. |
| Source-application packet tunnel | `NEPacket.metadata` when supplied, for traffic selected by the per-app configuration | A separate macOS per-app manager and app rules are required. App-scoped compositions use this separate capture mode. |
| App proxy or transparent proxy | Source app metadata at flow admission, TCP or UDP endpoints, and sometimes `remoteHostname` | macOS documents the hostname for connect-by-name APIs. A literal socket endpoint can have none. A transparent proxy handles streams and datagrams and needs its own provisioned provider capability. |
| TLS or QUIC handshake | Protocol-dependent client-advertised names and application protocols when visible | These are peer-supplied hints. Names can be absent, concealed, or shared across services. Established encrypted streams do not expose individual HTTP requests. |

The app and system extension currently declare packet-tunnel and DNS-proxy capabilities. Whole-Mac capture passes packet bytes without an application identity. A source-application capture configuration can also pass a verified alias and process incarnation. The monitoring inspector counts sockets with matching local addresses and derives friendly names from processes. Its sampled results and helper-name cleanup are appropriate for display. ## DNS provenance and resolver transport

The current DNS proxy accepts TCP and UDP, extracts one question, and selects an exact, suffix or glob rule from the connected profiles' ordered policy. A selected resolver rule tries its configured IPs on port 53. Exhaustion returns SERVFAIL. An original-resolver rule uses the incoming endpoint. Reply checks cover the transaction ID, response flag, opcode and question tuple, with an exception for error replies without questions. The parser currently does not walk answer records, aliases, signatures or TTLs. The forwarding decision takes no originating application ID. [Policy assembly](../SimpleVPN/ControlPlane/VPNController+DNSQueries.swift) · [DNS proxy](../PacketTunnel/DNSQueryProxyProvider.swift) · [Forwarder](../Shared/DNSQueryForwarder.swift) · [Wire parser](../Shared/DNSWireMessage.swift)

The selected profile ID identifies the rule's owner. The upstream exchange creates an ordinary `NWConnection` with TCP or UDP parameters. Two companies can both use `10.0.0.53`. Selecting that address alone leaves the kernel free to use whichever route owns it. A rule promising a particular VPN needs a resolver transport bound to that VPN, with its generation verified against the selected member. A required interface can scope a distinct interface. Multiple member tunnels behind one virtual interface require a member-specific DNS exchange inside the router. Preserve original interface scope when forwarding an unmatched query to a scoped resolver. On loss of the required member, fail the affected lookup without trying another tenant's resolver. [Exchange](../Shared/DNSQueryTransport.swift) · [Virtual composition's current resolver restrictions](../Shared/VirtualRoutingConfig.swift)

A correlation cache can record the normalized question, validated answer chain, resolver endpoint and scope, member generation, address family, returned addresses, and expiry from the shortest relevant TTL. Scope records by listener and policy generation. Record only solicited, complete, successful answers for the matching question and class. Ignore unrelated additional records and validate compressed names, alias loops and record lengths. Keep competing names for the same address. A shared CDN IP or a sole recent lookup gives a candidate name. Neither establishes which hostname a socket requested. Cache hits outside the proxy, literal addresses, mDNS, and encrypted DNS over HTTPS, TLS or QUIC can supply no observable lookup at all. [DNS terminology](https://www.rfc-editor.org/rfc/rfc9499) · [DNS over HTTPS](https://www.rfc-editor.org/rfc/rfc8484)

### How to rank a real-address lookup

At flow admission, retrieve all unexpired answer records containing the real destination in the same address family, network generation and resolver scope. Evidence from an incompatible scope is ineligible. If the packet lacks the scope, keep the competing scopes visible as ambiguous. Do not invent an exact match by assigning the packet to the most recent resolver.

For display, rank a matching verified requester instance first, then a verified common responsible application or observed process ancestor, then scope-only evidence. Within each class show the most recent eligible answer first. Keep the actual observation time, expiry and the number of distinct names and tenants. Use an explicit unknown identity for a query issued by a resolver daemon unless the API conveys an original requester. A later handshake can corroborate one candidate. Store the timestamp of that observation so replaying a decision cannot accidentally use evidence from the future.

For example, a parent process looks up `intranet.example.test`, then spawns a helper that connects to the answer two seconds later. A second app has also resolved a different hostname to that IP. Where both process generations and the ancestry edge are known, Explain can prefer the intranet candidate and show the competing name. Where only raw packets are available it shows both candidates with unknown requester. In both cases the authorized destination or alias policy makes the egress decision. A PID lookup performed after process exit cannot reconstruct that attribution.

## Synthetic DNS addresses and the return path

For an explicitly selected DNS namespace, an opt-in allocator can return a local synthetic A or AAAA address. A live mapping would identify the listener, original question and family, validated real address, resolver scope, selected VPN member and generation, and policy revision. The address proves which mapping was used. Any client that learns or guesses it can attempt a connection. Application authorization still requires trustworthy evidence from that connection. DNS flow metadata cannot supply it retroactively.

1. Reserve capture prefixes for IPv4 and IPv6, check for overlap with physical and VPN routes, configured DNS servers, peer endpoints and capture addresses, then install the capture before issuing answers. The existing virtual interface already uses `198.19.255.1` and `fd6e:7853:ffff::1`. A generation change must invalidate old leases safely. The capture must drop unmapped addresses throughout start, stop and policy transitions. [Capture configuration](../Shared/VirtualRoutingConfig.swift)
2. Resolve through the selected member, validate the reply, then publish the mapping to the data path **before** returning its synthetic address. An authenticated control channel must bind publication and acknowledgment to the same routing instance and revision. Packet and DNS providers can restart independently. Their shared extension bundle and App Group do not establish a live mapping or order events. If the acknowledgment or capture is missing, fail the scoped query.
3. On a new flow, resolve the synthetic destination to its real address and check member policy against the **real** destination. Apply destination NAT to the server address and source NAT to the member's local address. Save the original and translated tuples with the member generation before emitting the packet. If distinct originals would produce an identical reverse tuple on that member, allocate a translated port with a matching reverse entry or refuse the new flow.
4. On return, require the member, generation and translated reverse tuple to agree. Restore the synthetic server source and the original client destination and port. Apply the corresponding translations to quoted packets in ICMP errors, including Packet Too Big. Update IPv4, TCP, UDP and ICMP checksums as applicable, retain IPv6 UDP checksum requirements and preserve fragment association in both directions. The current router already scopes replies and reassembly by member generation and translates source addresses. Synthetic destination translation also changes its reverse key and quoted headers. [Packet router](../Vendor/proxy-engine/src/packetrouter/router.go) · [Packet translation](../Vendor/proxy-engine/src/packetrouter/packet.go) · [ICMP](../Vendor/proxy-engine/src/packetrouter/icmp.go) · [Fragments](../Vendor/proxy-engine/src/packetrouter/fragments.go)

An administrator can allow a corporate private range through a named member. Apply that member's real-destination allowlist after DNS resolution, including CNAME targets and any rebinding on refresh. Treat loopback, link-local control services, the provider's own transport endpoints and synthetic pools as separate local destinations. A matching hostname must not grant access to them by itself. For a literal private IP present in two members, a distinct listener, verified application rule or explicit member selection can disambiguate. Otherwise the route follows the configured behavior for an ambiguous destination.

Pin the translation for each established connection until it closes or times out. DNS expiry ends eligibility for new flows according to the lease policy. Clients can retain numeric addresses beyond TTL, and some explicitly cache them indefinitely. An alias recycled into another security domain can reach the wrong tenant even after every local timer has expired. Keep pools disjoint across security domains or decline allocation when safe reuse cannot be established. Withdraw capture only after callers can no longer route synthetic traffic onto a physical or different VPN default, or retain a discard route.

Preserve NXDOMAIN, NODATA, truncation and authoritative errors. Synthesis changes the answer's contents and invalidates original DNSSEC signatures. Preserve authentic data in a pass-through mode or decline synthesis where the client requires validated answers. Clearing AD alone cannot satisfy a validating client. Give explicit treatment to CNAME/DNAME, HTTPS/SVCB address hints, and DNS64/NAT64. A real address in an HTTPS hint or the other family's Happy Eyeballs response can circumvent a synthetic-only route. Unsupported cases need an explicit pass-through or refusal according to the rule's privacy requirement. [DNSSEC](https://www.rfc-editor.org/rfc/rfc4035) · [Service bindings](https://www.rfc-editor.org/rfc/rfc9460) · [Happy Eyeballs](https://www.rfc-editor.org/rfc/rfc8305)

## TLS, QUIC and decision timing

A TCP SYN precedes the TLS ClientHello. Once an upstream SYN goes through a member, the peer and NAT state are committed. To choose the member from a ClientHello, a local stream proxy must finish the client-side TCP handshake and buffer a bounded, time-limited preface before dialing upstream. A packet-forwarding router can use earlier facts such as a synthetic mapping or apply a declared fallback. A later name can trigger a deny or a fresh connection. Moving that established byte stream to another member risks disclosure and breaks transport state.

For TLS, parse complete handshake messages across TCP segments and TLS records. Visible SNI reports the name supplied by the client. TLS 1.3 encrypts the server certificate and negotiated ALPN after ServerHello. The visible ClientHello ALPN list is an offer. Encrypted ClientHello can expose an outer public name while hiding the requested inner name. HTTP/2 and HTTP/3 connection reuse can carry traffic for multiple authorized origins on one connection. A routing rule cannot infer subsequent encrypted HTTP hostnames, paths or new users from the first handshake. No interception certificates or session keys are required for the evidence described here. [TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446) · [Encrypted ClientHello](https://www.rfc-editor.org/rfc/rfc9849) · [HTTP/2 connection reuse](https://www.rfc-editor.org/rfc/rfc9113#section-9.1.1)

QUIC often puts the start of the handshake in the first UDP datagram. Reading it requires version-specific Initial packet protection removal, authentication of the packet under the public Initial keys and bounded CRYPTO-frame reassembly. Those keys do not establish peer identity. Handle reordered or missing frames, Retry and version negotiation, unknown versions and ECH. If classification must precede egress, hold the datagrams until a declared deadline or byte limit, then apply the policy for missing evidence. Rekeying, connection-ID changes or address migration are insufficient grounds to attach an unrelated tuple to a privileged route. Normal routing should skip handshake inspection when no rule requests it. [QUIC TLS](https://www.rfc-editor.org/rfc/rfc9001) · [QUIC migration](https://www.rfc-editor.org/rfc/rfc9000#section-9)

## Application identity and process lineage on macOS

The installed macOS 27.2 SDK documents the following distinctions.

| API | Meaning for a matcher |
| --- | --- |
| `NEFlowMetaData.sourceAppSigningIdentifier`, `sourceAppUniqueIdentifier` | The signing identifier can be empty for system processes and is commonly a bundle ID. The unique identifier identifies a particular binary build and can change on update. Use a signing requirement to distinguish software from different signers that presents the same identifier. |
| `NEFlowMetaData.sourceAppAuditToken` | Optional kernel-supplied identity for the source process of the flow. On macOS, resolve a code object using `SecCodeCopyGuestWithAttributes` and `kSecGuestAttributeAudit` and verify its designated requirement. Where useful, `proc_pidpath_audittoken` can recover the path for that process generation. Treat process exit, missing tokens and denied inspection as unknown. |
| `NETunnelProviderManager.forPerAppVPN()`, `appRules`, `NEAppRule.matchTools` | macOS supports per-app tunnel configurations. A rule uses a signing identifier and designated requirement. By default its helper scope includes apps' spawned helpers. A tool rule narrows the match, with Terminal launching curl as Apple's documented example. Test delegated and independently launched services separately. |
| `NEAppProxyFlow.remoteHostname`, `NEFlowMetaData.filterFlowIdentifier` | A connect-by-name hostname and an optional corresponding content-filter flow ID. Neither provides a universal join between a DNS request, an ordinary packet-tunnel flow and a later socket. |
| `proc_pidinfo` and Endpoint Security | A current parent PID is a snapshot. Reparenting, short-lived wrappers, exec and PID reuse can change the result. Endpoint Security provides parent and responsible audit tokens on sufficiently new event versions, with a separately entitled client and its own deployment requirements. The current app has no such entitlement. A responsible process can be the process itself. |

Apple's source-application tunnel restriction, flow metadata limits, per-app rules and tool semantics appear in `NEPacket.h`, `NEFlowMetaData.h`, `NEAppProxyFlow.h`, `NETunnelProviderManager.h` and `NEAppRule.h`. Process-token APIs appear in `SecCode.h`, `libproc.h`, `bsm/libbsm.h` and `EndpointSecurity/ESMessageCore.h`. [NEPacket metadata](https://developer.apple.com/documentation/networkextension/nepacket/metadata) · [NEFlowMetaData](https://developer.apple.com/documentation/networkextension/neflowmetadata) · [NEAppRule](https://developer.apple.com/documentation/networkextension/neapprule) · [Endpoint Security](https://developer.apple.com/documentation/endpointsecurity)

Evaluate identity at flow admission. Cache signature verification by audit token/process generation within a short, bounded window. Distinguish the kernel-attributed source, a verified named helper, and a best-effort parent snapshot. An executable name, a path alone, a sampled PID or a DNS client's signing ID cannot satisfy a rule requiring a verified app or ancestor. A transparent proxy that accepts a flow owns its transport and may produce a new outbound tuple under the provider's identity. Any cross-provider correlation therefore needs explicit authenticated continuity. On a transparent proxy, returning false permits direct communication under the SDK contract. A policy requiring a deny must explicitly close or reject the captured flow. [Transparent proxy](https://developer.apple.com/documentation/networkextension/netransparentproxyprovider)

### App and running-process routing in SimpleVPN

In **Manage VPNs**, select a compatible VPN and choose **More VPN Actions → Route Apps Through This VPN…**, or create a composition with app routing. Add a signed app or inspect a running process, then select its VPN. A destination override sends an IP or subnet to a different member for that source. Saving records the choice. Connecting installs a per-app configuration for one to sixteen compatible VPNs. Other apps retain their macOS routing. Each member enforces its own egress restrictions, including Allowed IPs for WireGuard. Source-routed sessions use a separate configuration version so an older extension refuses to run them. [Supported providers and settings](RoutingAtlas.html#provider-routing)

The controller creates a per-app tunnel manager and verifies its installed app rules. The provider independently checks its routing method and rule set before accepting start options. Selected apps share the interface's DNS settings. Members with differing resolver configurations are rejected. The interface captures both address families for the selected apps, independently of the whole-Mac gateway and DNS elections. When macOS captures a selected app's packets but omits the necessary metadata, those packets drop.

The capture provider reads `NEPacket` objects. macOS selects traffic with the executable’s original designated requirement. On the first observation of an identity, a signed, on-demand XPC service independently checks the kernel audit token and the executable's designated requirement. The provider prefilters candidates using the reported signing identifier. Tokens and process overrides travel in start options only. The service never receives packet contents or decides a VPN. A selected process overrides its persistent app rule. A later generation reusing its PID cannot match. macOS scopes capture by executable, so sibling instances captured by the same OS rule can be dropped when they have no route of their own.

The packet pump caches verified aliases per token, signing identifier and binary identity for 15 seconds, and negative answers for one second. It coalesces a pending lookup for that identity, limits the buffer to 64 packets per identity and 1 MiB total, and applies a drop when a timeout or bound is reached. One busy app cannot make other verified apps wait. The Go connection table pins the VPN and owning process generation. Conflicting owners of an indistinguishable transport tuple quarantine the flow. Ordinary destination routing uses its original packet reader and makes no identity-service calls.

Persistent signed-executable rules can require a kernel-verified executable name or path and a current same-user ancestor executable path. The helper rechecks the chain before returning a match. The running-process picker also displays a short same-user parent snapshot. Reparenting, process exit and delegated OS traffic limit what current ancestry proves. Historical ancestry would require a lifecycle event source such as Endpoint Security and its own deployment permissions. [App rules](https://developer.apple.com/documentation/networkextension/neapprule) · [Flow metadata](https://developer.apple.com/documentation/networkextension/neflowmetadata)

For a configured `HTTP_PROXY` or `http_proxy` condition, the helper compares a credential-free endpoint with launch evidence for the attributed process. It returns matched, different or unavailable. Absence, an inaccessible environment, credentials in the value, and duplicate entries cannot authorize a match. The VM receives the admitted source-rule ID. Configured proxy information does not establish which remote endpoint the client actually contacted. In particular, curl handles HTTP via the lowercase variable. A controlled Apple curl launch on the development Mac returned unavailable for its known uppercase setting.

### Installed-system acceptance

Use an unmanaged test Mac and confirm the active system extension matches the build being tested. Configure two test WireGuard peers with the same private destination. Select two independently signed clients in a per-app composition, bind each to a different peer, and compare peer-side captures for new IPv4 and IPv6 TCP and UDP connections. Repeat with the UI closed while keeping the tunnel active, a temporary process and its relaunched instance, a helper, and a delegated URL session. Open the same destination from an unselected client to check the rest of the Mac's routing. Change an override, reconnect, and confirm both the selected source and the observed egress. Exercise a stopped member and an unavailable helper. Record missing metadata, captured drops, and traffic macOS never delivered as different outcomes.

The automated tests cover signed XPC inspection, real child-process lifetime, installed-rule representation, bounded packet admission and routing through two encrypted loopback peers with source metadata provided at the capture boundary. Those tests do not establish that a particular installed macOS release will attribute every application's traffic. ## Privacy and acceptance

Collect the minimum facts used by active rules. With no name or application rule, avoid per-flow DNS history, process scans, signature lookups and TLS/QUIC parsing. Bound both individual entries and total memory across clients. Keep lookup histories, real-to-synthetic mappings, token-derived identities and packet prefaces in memory. Normal diagnostics can report counts, capacity, expiry, rule IDs and classes of missing evidence without recording query names, SNI, app paths, usernames, addresses or payload.

| Scenario | Acceptance criterion |
| --- | --- |
| Two members use the same resolver IP, server IP and hostname | Isolated listener/member queries reach their intended resolver. Replies with the wrong member generation cannot resolve or receive the other's flow. |
| A permitted name changes from an allowed member address to a local control address | The existing flow stays pinned. A new resolution or flow cannot gain access to the newly returned target solely from the name. |
| Two names share a CDN address and one requester uses cached or encrypted DNS | A rule requiring the requested name receives unknown/ambiguous evidence and uses its configured behavior. Timing does not pick the winner. |
| DNS reply races capture installation, provider restart or tunnel removal | No synthetic answer is released before mapping acknowledgment. Unmapped and obsolete destinations cannot leave through the default route. |
| Two synthetic names map to one real endpoint and the same original source port | An unambiguous reverse translation or an explicit refusal. Foreign replies, quoted ICMP, stale generation and late fragments cannot cross flows. |
| Client holds a numeric alias beyond TTL while the pool fills | An established flow retains its original member. A later attempt cannot reach a different tenant using the old alias. Pool exhaustion is observable without logging names. |
| Dual-stack HTTPS/SVCB and DNSSEC | Neither address family nor service hints create an unintended direct path. Modified records never assert upstream authentication. A validating client receives authentic data or the documented failure. |
| Split TCP ClientHello, coalesced HTTP/2, ECH, reordered QUIC Initial or unknown QUIC version | No first packet leaves a private route before an evidence-dependent decision. Classification stops at its limits. Hidden or unobserved names remain unknown. |
| Two signers reuse an identifier and a child exits and its PID is recycled | Signing requirements and token generations distinguish identities. Missing or reused PIDs cannot satisfy a verified-app rule. Test a signed helper launched by its selected app and the same helper launched independently. |
| Lightweight operation and diagnostic export | Measure idle wakeups with all optional features off, cap memory under DNS bursts and partial handshakes, and verify diagnostic fixtures contain none of the input names, app paths or packet payloads. |
