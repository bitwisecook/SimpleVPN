SimpleVPN Help

Every option explained in plain language: what it does, when to change it, and what can go wrong. Options apply per-VPN and take effect the next time that VPN connects. An option you never change follows the OpenVPN engine's default — including when a future update improves that default.

Importing VPNs

SimpleVPN imports standard OpenVPN configuration files (.ovpn). Four ways, all equivalent:

  • Drag and drop a file onto any SimpleVPN window.
  • Double-click a .ovpn file in the Finder (or drop it on the Dock icon).
  • File ▸ Import, or the + button in Manage VPNs.

SimpleVPN checks the file with the same parser the tunnel uses, so a file that imports will also connect. If you import a file you already have, nothing is duplicated — SimpleVPN tells you which VPN already has that configuration. A file with the same name but different contents imports alongside the original with a numbered name.

Your Own VPN Order

The VPN list starts in the order your VPNs were added, and you can put it in your own order instead. Manage VPNs is where you do it: drag a VPN up or down, use the up and down buttons beside + and −, or right-click a VPN and choose Move Up or Move Down. All three do the same thing, and the order you arrange is the order everywhere — the main window’s list shows the same arrangement, because there is only one.

The list is grouped by what connecting something does to this Mac: Whole-Mac VPNs change where all this Mac’s traffic goes, and Local Ports open a port that nothing uses until you point an app at it. Moving a VPN keeps it in its own group. That is deliberate: which group a VPN is in follows its own settings — an SSL VPN with Run In-Process turned on is a whole-Mac VPN, and the same VPN with it turned off is a local port — so dragging a row across the line would change what connecting it does, silently, by a gesture. The way to move it is the setting that decides it. The first VPN in a group has no Move Up, and the last has no Move Down; both say so rather than doing nothing.

A VPN added later has no place in your arrangement yet, so it appears at the end of its group rather than taking somebody’s first slot. Your arrangement travels with an exported setup, so a second Mac gets the list in the order you put it in.

Servers & the Map

A configuration file can list more than one server. By default SimpleVPN lets OpenVPN try them in order until one answers. The map and the server menu in the main window let you pin one server instead — useful to pick a nearby country or a server that works on your current network.

Choosing a server simply sets the Server, Port and Protocol options for you; choosing Automatic clears them again. Server locations are country-level (see Privacy Notes), so pins sit at the centre of their country.

Putting the servers in your own order

Left alone, SimpleVPN orders every server list for you: quickest first where it has measured them, nearest first where it hasn’t, and anything it can neither measure nor place last. The footnote under each list says which of those you are looking at.

In the VPN editor’s Servers tab you can put them in your own order instead — drag a row, use the up and down buttons beside + and − (⌘⌥↑ and ⌘⌥↓), or right-click a row and choose Move Up or Move Down. Once you have, your order wins everywhere: the table and the server menus both show the list you arranged, in your order — the menus still head their sections with the region each server is in, so a region can appear more than once rather than your order being quietly rearranged into continents. Speed checks keep filling in the Speed column but stop rearranging the rows — the automatic ordering and a hand-made one cannot both be in charge, and yours is the one you asked for.

Use automatic order appears beside the buttons once you have arranged the list, and hands the ordering back to SimpleVPN.

Two things worth knowing:

  • Servers that come from the VPN’s configuration can be moved like any other. The lock on those rows is about existence, not position: only the configuration can add or remove them, and moving one changes the order SimpleVPN offers it in without touching the configuration file. Where OpenVPN itself falls back from one remote line to the next, it still follows the file.
  • A server that turns up later — because you re-imported a configuration that lists a new one — has no place in your order yet, so it sits at the end until you give it one, rather than taking somebody else’s first-choice slot. The footnote says how many are waiting there.

Certificates & Keys

The Certificates tab of the VPN editor shows what's embedded in the configuration — certificate authority, your client certificate and private key, and any extra TLS key — as readable cards: names, issuer, organisation, expiry, and the web addresses a certificate covers. A red badge means expired; an orange badge means it expires within 30 days.

Drop a certificate or key file on the matching well and SimpleVPN converts it and embeds it into the configuration for you. Accepted formats: PEM (.pem, .crt, .key), DER (.cer, .der), PKCS#12 bundles (.p12, .pfx — you'll be asked for the bundle password), and OpenVPN static keys. The format is detected from the file's contents, not its name — if you drop a key on the certificate well, SimpleVPN offers to put it in the right place.

Pausing a VPN

Pause stops VPN traffic without tearing the connection down: the secure (TLS) session is kept alive, so resuming does not ask you to sign in again — no password, no verification code. Two kinds of pause:

  • Pause — Block Traffic (the default): the VPN's routes stay in place, so traffic that would use the VPN simply waits/fails. Nothing leaks. Right for stepping away briefly.
  • Pause & Send Traffic Outside the VPN: the VPN's routes and DNS are removed, so everything uses your normal connection until you resume. This deliberately sends traffic outside the VPN — the red banner stays up the whole time as a reminder.

Limits worth knowing:

  • Servers eventually expire idle sessions. If yours does, resuming triggers a silent reconnect using your remembered credentials or the server's session token — and if the VPN needs a fresh verification code and no session token is available, you'll simply be asked to sign in again.
  • For the most reliable resume across network changes and sleep, turn on Stay connected through interruptions.
  • A pause never outlives the connection: disconnecting (or a system-initiated stop) clears it.

While connected, SimpleVPN watches the connection passively (no test traffic is sent): if your Mac keeps sending but nothing comes back — a train entering a tunnel, hotel Wi-Fi dying — the status shows the interruption and, together with Stay connected through interruptions, recovery happens automatically when the network returns.

The Connection Doctor, shown on the connection window, turns these observations into named problems with a one-tap fix. Each card links to the matching section below. Fixes that trade a little security for reachability (allowing older ciphers, blocking a protocol the tunnel doesn't carry) are marked in amber, and every fix is reversible from the VPN's settings.

Large transfers stall (MTU / fragmentation)

Symptom: small pages and pings work, but large downloads, file copies or e-mail with attachments hang and eventually time out. The throughput graph shows you sending steadily while almost nothing comes back.

Cause: the tunnel adds its own headers, so a full-size packet that fit on the underlying network is now too big and gets fragmented. Many networks silently drop the oversized packet and the "please fragment" (ICMP "fragmentation needed") message that would let your Mac shrink it — a "PMTUD blackhole". Small packets slip through; big ones vanish.

Fix: the Doctor sets mssfix, which caps the size of the data each end offers so packets always fit — for TCP traffic (the large transfers that stall) this is invisible apart from things starting to work. If the Doctor measured your path it uses the exact value; otherwise it uses a safe 1360. You can adjust or undo it from the VPN's settings.

IPv6 traffic may bypass the VPN

Symptom: the tunnel is up, but a "what's my IP" site that supports IPv6 still shows your real address and location.

Cause: this tunnel only carries IPv4, yet your Mac still holds a public IPv6 address on Wi-Fi or Ethernet. IPv6-capable sites are reached over that address, outside the VPN — so they see where you really are.

Fix: the Doctor turns on block traffic the VPN doesn't carry, which stops your Mac using IPv6 while the IPv4-only tunnel is connected. The proper long-term fix is a tunnel that carries IPv6 too; ask your administrator.

Website lookups may be leaking (DNS)

Symptom: your traffic is protected, but a “DNS leak test” site shows your internet provider's or local network's DNS servers rather than the VPN's.

Cause: everything is routed through the VPN, but the VPN didn't hand your Mac a private DNS server — so the names of the sites you visit are still being looked up by whoever runs the local network, revealing where you're browsing even though the traffic itself is encrypted.

Fix: there's no safe automatic fix, so the Doctor explains it. The proper fix is server-side: the VPN's administrator should push a DNS server (OpenVPN dhcp-option DNS …). As a stopgap you can set a trusted DNS server manually in System Settings ▸ Network.

Local devices unreachable while connected

Symptom: once connected you can no longer reach your printer, network drive, router page or other devices on your home or office network.

Cause: this is a full-tunnel VPN — all traffic, including to your own local network, is routed through the tunnel, where those local addresses don't exist.

Fix: the Doctor turns on local network access, which keeps traffic to private local addresses on your real network while everything else stays in the tunnel. Some administrators disable this deliberately; if it's re-blocked after connecting, that policy is being enforced server-side.

This network blocks the VPN's UDP traffic

Symptom: the VPN never connects — or only connects on some networks (home works, the café or hotel doesn't).

Cause: the VPN's usual UDP packets are being dropped by the network, while ordinary web traffic on TCP port 443 still works. Guest, hotel and airport Wi-Fi commonly allow only web ports.

Fix: the Doctor switches the VPN to TCP on port 443, so it looks like normal secure web traffic and usually gets through. UDP is faster, so you may wish to switch back on networks where it works.

Keeps asking for a new code after connecting

Symptom: you connect fine, then minutes or an hour later the VPN drops with a sign-in failure, even though nothing changed.

Cause: OpenVPN renegotiates its keys on a timer, and by default that re-runs the whole sign-in. With a verification code that code is already spent, so the re-authentication fails.

Fix: the Doctor sets reneg-sec 0 to stop the client forcing a re-sign-in. The cleaner fix is server-side: the administrator enables session tokens (auth-gen-token) so the first code is exchanged for a token and never demanded again — see Session Tokens.

Couldn't agree on an encryption cipher

Symptom: the connection fails during setup with a message mentioning the cipher or "data channel".

Cause: SimpleVPN offers modern AEAD ciphers (AES-GCM, ChaCha20-Poly1305) by default. An older server may only offer an older cipher such as AES-CBC, so the two can't agree.

Fix: the Doctor allows older data ciphers so a shared one can be negotiated. AES-CBC is still secure; this is marked amber only because newer is preferable. The real fix is for the server to offer a modern cipher.

The server's identity couldn't be verified

Symptom: the connection is refused with a certificate or verification error.

Cause: the server presented a certificate SimpleVPN doesn't trust — expired, self-signed, issued by a private authority, or the CA in your configuration is missing, wrong, or out of date.

Fix: there is no safe automatic fix, so the Doctor only explains it. Contact the VPN's administrator for the correct CA or an updated configuration. Do not weaken certificate strictness to get past this unless they explicitly tell you which setting to change — a verification failure is exactly what protects you from connecting to an impostor server.

Drops when the connection goes quiet

Symptom: the VPN disconnects after periods of no activity — you come back to your Mac and it's dropped.

Cause: firewalls and NAT routers forget connections that have been idle for a while, and the tunnel is torn down.

Fix: the Doctor adds a small keepalive (a heartbeat every 10 seconds, giving up after 60) so the tunnel stays alive through quiet periods. Pairing this with Stay connected through interruptions gives the most resilient connection.

A Wi-Fi sign-in page is blocking the connection

Symptom: on a new Wi-Fi network the VPN won't connect, and web pages redirect to a "accept terms" or "sign in" screen.

Cause: this is a captive portal — the network holds all traffic hostage until you complete its sign-in page in a browser.

Fix: open any website (try a plain http:// address), complete the network's sign-in or terms page, then connect the VPN. The Doctor only detects and explains this; there's nothing to change in the VPN's settings.

Moving to Another Mac

Settings ▸ General ▸ Export & Import writes every VPN and every SimpleVPN setting to one file, and reads one back. Name the file .yaml or .json and you get that encoding — they carry exactly the same thing, so pick whichever you would rather read.

  • No passwords or keys are in the file
  • What importing does, and what it will not do
  • On a managed Mac

Inside the file, a name like openvpn.port or wg.endpoint is SimpleVPN's own name for that setting. Those names never change, so a file keeps working even when a label on screen is reworded — and you can look any of them up in this manual.

No passwords or keys are in the file

Nothing secret is ever written, and there is no option to include it: an exported file leaves every protection SimpleVPN has — mail, a shared folder, a repository, a backup — and cannot be recalled once it exists. Everything left out is recoverable, because it is still in this Mac's keychain and whoever set up the VPN can issue it again.

The file lists what it left out and what to do about it, both at the top and under each VPN. After importing, type the missing password or key in once and the VPN is complete. Public material is included — a certificate authority decides who your tunnel trusts, so it belongs where you can read and compare it.

If you want a backup that includes your secrets, that is a different thing and is not this: keep using Time Machine and your keychain, or ask your VPN's owner for the original files.

What importing does, and what it will not do

  • It shows you the changes first. Every setting that would change, with its before and after; every VPN that would be added, with its server address, its pinned certificate or host key, and anything else that decides where traffic goes and who is trusted. Nothing happens until you say so.
  • VPNs are added alongside yours. Nothing is replaced. A VPN whose name you already use arrives as “name (imported)”, so you can compare the two and delete whichever you don't want.
  • Your current settings are saved first. Before anything changes, SimpleVPN writes them to ~/Library/Application Support/SimpleVPN/Recovery and reads the file back to check it. If that fails, the import doesn't start.
  • It never turns verification off. A file asking SimpleVPN to stop checking a host key or a certificate has that VPN refused outright, and says which setting was the problem. SimpleVPN has no such option anywhere and will not take one from a file.
  • It never turns on a macOS permission. Location stays as you have it: macOS asks for that permission when you turn the switch on, and a file must not answer for you.
  • Anything it doesn't understand is reported, not guessed at. An unknown kind of VPN, a value of the wrong type, or a file written by a newer SimpleVPN is refused with a reason. One bad VPN in a file does not stop the others.

Labels come along too. A label you already have keeps the name and colour you gave it.

On a managed Mac

If your organisation has locked SimpleVPN's settings, both buttons are unavailable and say so: a managed Mac may forbid configuration leaving the device at all.

Privacy Notes

  • Server locations come from a country-level IP database bundled inside the app (IP Geolocation by DB-IP, refreshed with app updates). No server information leaves your Mac; only a normal DNS lookup of the server name happens.
  • Your public address ("appears from…") requires asking an internet service what address it sees. SimpleVPN does this at launch, when a VPN connects or disconnects, and about every five minutes while a window is open. Turn it off entirely in Settings ▸ Privacy ▸ "Look up my public address" — off means those requests are never made (the map's you-are-here pin and the public-address rows simply disappear). Nothing else is sent.
  • Secrets (passwords, proxy and private-key passwords) live only in your Keychain. They are never stored in VPN configuration files or system preferences.

Server

Default: the server in the configuration file.

Connects to a different server address than the one built into the configuration file, without editing the file. Useful when your provider gives several interchangeable servers, or an administrator asks you to test a specific one.

The certificate checks still expect the same organisation's server — pointing this at an unrelated server will (correctly) fail verification.

Port

Default: the port in the configuration file (OpenVPN's usual port is 1194).

Connects on a different port. The most common reason: restrictive networks (hotels, airports, corporate guest Wi-Fi) often block everything except web traffic — if your provider listens on port 443 too, setting port 443 with TCP usually gets through.

Protocol

Default: whatever the configuration file says (usually UDP).

How OpenVPN's packets travel to the server:

  • UDP — fastest and best for streaming and calls. Some networks block it.
  • TCP — slower under packet loss, but passes through nearly every network, especially on port 443 where it looks like ordinary secure web traffic.
  • Adaptive — tries UDP first and falls back to TCP automatically.

While an HTTP proxy is configured, only TCP can be used — proxies can't carry UDP.

Internet Protocol

Default: Automatic.

Forces the connection to the server over IPv4 or IPv6. Leave on Automatic unless one of them is broken on your network — for example, some networks advertise IPv6 but don't actually route it, which can make connecting slow or flaky; forcing IPv4 fixes that. This only affects how you reach the server, not what traffic the tunnel carries (see Traffic the VPN Doesn't Carry).

Connection Timeout

Default: keep trying forever.

How long to keep trying before giving up when the server doesn't answer. "Keep trying forever" is right for a VPN you want up whenever possible; a short timeout is better when you connect on demand and want a fast, clear failure instead of a spinner.

Stay Connected Through Interruptions

Default: off.

Keeps the VPN tunnel alive when your Mac changes networks or wakes from sleep — switching between Wi-Fi and hotspot, a train going through a tunnel — instead of tearing everything down and starting over. Reconnection is faster and apps usually don't notice the gap.

Worth turning on for laptops that move around. The trade-off is negligible for most people: while the network is gone your traffic waits rather than failing immediately.

Connect Through an HTTP Proxy

Default: off — SimpleVPN reaches the server directly.

The master switch for the proxy fields below. Turn it on when this network makes you reach the internet through a proxy, and the proxy's address, port and sign-in appear underneath. Turning it off again clears all of them, so a proxy you have stopped using can't be left half-configured.

Proxies carry TCP only: while a proxy is configured, the Protocol effectively becomes TCP, and a VPN left on UDP never uses the proxy at all.

Proxy Host

Default: no proxy.

Reaches the VPN server through an HTTP proxy — common on corporate networks where direct outbound connections are blocked and everything must pass through a proxy. Enter the proxy's name or address here and its port next to it; your network's IT documentation will have both.

Proxies carry TCP only: while a proxy is configured, the Protocol effectively becomes TCP.

Proxy Port

Default: none — required once a proxy host is set.

The port the proxy listens on. Common values are 8080, 3128, or 80.

Proxy Username

Default: none.

Only needed if your proxy requires sign-in. The proxy password is stored in your Keychain, never in the configuration.

Proxy Password

Default: none. Needs a proxy username first.

The password the proxy asks for. It is kept in your login keychain and handed to the engine in memory when the VPN connects — never written into this VPN's settings file, and never on a command line. Clear the field to remove the stored password.

Allow Unencrypted Proxy Sign-in

Default: off — only digest-style sign-in is offered.

Some proxies only support HTTP "Basic" authentication, which sends the proxy username and password essentially unencrypted on your local network segment (your VPN traffic itself stays encrypted). Turn on only if the proxy refuses to authenticate otherwise.

Anyone able to watch your local network can read the proxy credentials. Use a proxy password you don't use anywhere else.

Private Key Password

Only shown when this configuration's private key is encrypted.

Configuration files that carry a client certificate often protect its private key with a passphrase. Enter it once here and it is kept in your login keychain, so connecting doesn't ask again; it is never written into the VPN's settings file. Clear the field to remove the stored passphrase — the next connection will then fail to unlock the key, which is the honest outcome rather than a silent fallback.

Keep Retrying After a Failed Sign-in

Default: off — a rejected sign-in disconnects.

Treats a rejected sign-in as temporary and retries after a pause. Useful when the server occasionally rejects sign-ins under load, or with time-based verification codes that may expire mid-handshake. Leave off if you'd rather know immediately that your password is wrong.

Use Server Session Tokens

Default: on. Only shown for VPNs that sign in automatically.

Lets the server hand out a temporary session pass after the first connection, so quick reconnects don't need a full sign-in. Only relevant to "autologin" configurations (no username/password). Turn off only if your server's administrator says its session handling misbehaves.

Allow Local Network Access

Default: off — the VPN decides what is reachable.

Keeps devices on your home or office network — printers, file servers, smart-home gear — reachable while the VPN is connected, even when the VPN routes everything else through the tunnel. Turn on if printing or local file shares stop working when you connect. Security-conscious workplaces may prefer it off, so untrusted local networks can't reach your Mac's services while you're on the company VPN.

Traffic the VPN Doesn't Carry

Default: let the server decide.

Some VPNs only carry IPv4, or only IPv6. This decides what happens to the other kind of traffic:

  • Allowed outside the VPN — it uses your normal connection. Convenient, but that traffic is not protected: a website reachable over IPv6 could see your real address while your IPv4 traffic is tunnelled (a classic "IPv6 leak").
  • Blocked — traffic the VPN doesn't carry goes nowhere. More private; some sites may not load if they're only reachable over the blocked family.

Fall Back to Google DNS

Default: off.

Some VPNs route all your traffic but forget to provide DNS servers — then nothing can look up names and browsing appears broken. With this on, SimpleVPN falls back to Google's public DNS (8.8.8.8) in exactly that situation, so browsing keeps working.

The privacy trade-off is real: Google can then see your DNS lookups. If your VPN is correctly configured this setting never activates.

Minimum TLS Version

Default: the configuration file's minimum, or the system minimum.

The oldest encryption-handshake version you'll accept from the server. TLS 1.2 (2008) and 1.3 (2018) are both considered secure today; requiring 1.3 is the strictest choice and works with modern servers.

"No minimum" removes the floor entirely — including one set by the configuration file.

Only choose "No minimum" for a very old server you must reach, and treat that connection as weakly protected.

Note: this setting can raise the bar but never lowers one the configuration file already sets higher.

Certificate Strictness

Default: the configuration file's setting, otherwise the engine's preferred profile.

How strict to be about the quality of the server's certificate:

  • Modern — requires at least 2048-bit RSA signed with SHA-256. Right for anything set up in the last decade.
  • Legacy — additionally accepts 1024-bit RSA and SHA-1 signatures. Those are considered breakable; use only for old corporate servers you cannot avoid.
  • Suite B — a strict NSA-defined profile used by some government deployments. Everything else will fail to connect.

"Only if the configuration file doesn't specify" applies your choice as a fallback instead of an override — the file's own setting, if present, wins.

Compression

Default: off (compression stubs only) — recommended.

Compressing VPN traffic sounds appealing but is dangerous: the VORACLE attack (2018) showed that an attacker who can inject content into your traffic can steal secrets — session cookies, tokens — from a compressed VPN stream. Modern traffic is mostly already compressed or encrypted anyway, so the speed win is tiny.

  • Off — never compress. The safe choice.
  • Downloads only — accept compressed data from the server but never compress what you send. This avoids the known attack (which needs your uploads compressed) while staying compatible with servers that insist on compression.
  • Full — compress both directions.
"Full" re-enables the attack surface. Use only on a network you trust end-to-end, or when an administrator requires it.

If the configuration file itself asks for compression, "Downloads only" is the sensible compromise.

Allow Outdated Encryption

Default: off.

Permits ciphers that are obsolete and considered unsafe — Blowfish (BF-CBC), single DES, RC2. Some very old servers still use them. Turn on only if connecting fails with a cipher-related error and the server can't be upgraded — and treat the connection as weakly protected.

Allow Older Data Ciphers

Default: off — only modern ciphers (AES-GCM, ChaCha20-Poly1305) are offered.

Permits older-but-not-broken ciphers such as AES-CBC when the server can't use the modern ones. Unlike outdated encryption, these are still considered secure — just slower and no longer preferred. Turn on if a somewhat-old server refuses to negotiate a cipher.

TLS Cipher List

Default: empty — the engine's built-in selection.

An exact, colon-separated list of TLS (up to 1.2) cipher suites to offer, for servers with unusual requirements. This is an expert escape hatch: leave empty unless a server administrator gave you a precise string to paste. A wrong value simply prevents connecting.

TLS 1.3 Ciphersuites

Default: empty — the engine's built-in selection.

Same as the TLS cipher list, but for TLS 1.3 connections, which use a separate list. Leave empty unless told otherwise.

TLS Diagnostics

Default: off.

Adds TLS handshake detail to the connection log — useful when support is diagnosing certificate or handshake failures. Higher levels are very chatty. Turn back off afterwards; it only slows things down.

Use Blocking DNS Lookups

Default: off.

Changes how the server's name is looked up during connection (blocking instead of in the background). On unusual network setups — some proxies, some captive portals — the background lookup can misbehave and this fixes it. Otherwise it makes no visible difference.

Don't Send a Client Certificate

Default: off — the configuration's certificate is used.

Connects without identifying this Mac with its client certificate. Most servers that expect a certificate will refuse the connection; support may ask you to try this to isolate certificate problems, and a few servers genuinely run username/password-only.

Key Direction

Default: bidirectional.

Configurations using an extra HMAC key (tls-auth) have a "direction" that must complement the server's — 0 on one side, 1 on the other, or bidirectional on both. If the configuration file doesn't say and the server uses a direction, connecting fails with authentication-format errors. Only change on an administrator's instruction.

Addresses

Required. From your provider.

The IP address(es) this device is assigned inside the tunnel, each with a prefix length — e.g. 10.0.0.2/32 for IPv4, fd00::2/128 for IPv6. WireGuard has no dynamic address assignment; the server tells you exactly what to put here.

DNS Servers

Optional.

DNS servers to use while connected — usually one inside the tunnel so that private names resolve. Leave empty to keep your current DNS. Multiple servers are comma-separated.

Search Domains

Default: empty — only full names resolve.

The domains to try when you type a short name. With corp.example listed, nas is looked up as nas.corp.example; without it, nas finds nothing while nas.corp.example works perfectly. That asymmetry is the commonest “DNS is broken on this VPN” report, and it is not a fault in the tunnel — a WireGuard configuration file has no line for a search list, so there is nothing for SimpleVPN to read from the file your provider gave you. Type them here, separated by commas, in the order you want them tried.

Only used when DNS Servers is filled in: the search list belongs to the resolvers this tunnel advertises. Exporting the configuration for another WireGuard client leaves this out, because the format has nowhere to put it.

Allow local network access

Default: off.

Keeps the devices on the network you are physically on — printers, file servers, a NAS, smart-home gear — reachable while the tunnel is up. Turn it on if printing or local file shares stop working when you connect.

What leaves the tunnel: traffic to the networks your Mac's own interfaces are on, and to the addresses devices use to find each other (link-local and multicast, which is how AirPlay and Bonjour work). Nothing else. Anyone watching the network you are on can see that traffic, which is why it is off unless you ask for it, and why a workplace may prefer it off — with it on, an untrusted café network can also reach your Mac's own services.

SimpleVPN works out which networks those are when the tunnel connects, from the interfaces that are actually up, and it never guesses at a wider range. Joining a different network later does not move the carve-out; reconnect to pick up the new one.

MTU

Default: auto-detected (usually 1420).

The largest packet size the tunnel carries. WireGuard picks a sensible value automatically; set it lower (e.g. 1380 or 1280) only if some websites or transfers stall — a classic sign of MTU problems on the path. Anything from 576 to 1500 is accepted, because providers on PPPoE or behind double NAT do hand out 1200 or 1240 and those configurations work. Below 1280 the tunnel can carry IPv4 only: no IPv6 link may have a smaller MTU than that.

Listen Port

Default: chosen automatically.

The local UDP port WireGuard listens on. Leave empty and the system picks a free one; set it only if you're accepting inbound connections and need a fixed port.

Routing Table

Default: auto.

auto installs routes for the Allowed IPs so matching traffic goes through the tunnel (and, for a full tunnel, adds a rule to protect the tunnel's own packets). off installs no routes at all — only choose this if you're managing routing yourself. Custom takes a routing-table name (such as main) or a number: wg-quick passes it straight to ip route … table, which resolves names out of rt_tables. Only configurations you export use it — SimpleVPN's own engine ignores it.

Firewall Mark

Default: off.

A firewall mark (fwmark) stamped on the tunnel's own outgoing packets, for advanced policy-based routing setups. Almost nobody needs this — leave it empty unless you're deliberately building custom routing rules.

Private Key

Required. Kept in your Keychain; never shown again once saved.

This device's own secret key, as base64 (44 characters). It is the other half of the public key you gave — or registered with — your provider: WireGuard has no username or password, so these keys are the sign-in.

The field is write-only. It shows whether a key is stored, and typing or pasting a new one replaces it when you save; the stored value is never rendered back, so it can't end up in a screenshot or a screen share. Importing or pasting a .conf file sets it too.

Anyone holding this key can be this device on your provider's network. If it leaks, generate a new pair and register the new public key.

Peer Public Key

Required. From your provider.

The server peer's public key (a base64 string). WireGuard uses it to identify the server and encrypt to it — there are no usernames or passwords. If it's wrong, the handshake silently fails and nothing connects.

Server Address

Required.

Where to reach the server: host:port, e.g. vpn.example.com:51820. WireGuard is UDP, so the port matters.

Allowed IPs

Default: 0.0.0.0/0, ::/0 (full tunnel).

The destinations that go through this peer — WireGuard's routing and its cryptographic access control in one setting. 0.0.0.0/0, ::/0 sends all traffic through the tunnel (full tunnel). List specific subnets instead (e.g. 10.0.0.0/8) to make it a split tunnel that only carries those networks.

Pre-shared Key

Optional.

An extra symmetric key layered on top of the normal WireGuard key exchange, for defence against future quantum attacks. Both sides must share the same value. Only set it if your provider gives you one.

It is key material, so it is treated like the private key: the row says whether one is stored, never what it is. Paste a new value into Set / Replace Key to change it, or press Remove and save to take it off — clearing really clears, it doesn't leave the old key in the keychain.

Persistent Keepalive

Default: off.

How often (in seconds) to send a tiny keepalive so NAT routers and firewalls don't forget the tunnel and drop it. 25 is the usual value when you're behind NAT; leave it off on a server with a stable public address.

Exporting a Configuration

WireGuard settings can be written out as a standard wg-quick file, for a phone, a router, or another WireGuard client. There are two buttons, because there are genuinely two different files.

  • Export .conf… writes everything except your keys. Safe to mail, keep, or commit — but wg-quick refuses a configuration with no private key, so the person receiving it has to paste one in before it will run. Use this to hand over the server details, the allowed networks and the DNS settings.
  • Export .conf with Keys… writes a file that works as-is, because your private key (and pre-shared key, if you have one) are in it, unencrypted. SimpleVPN asks first and tells you exactly what will be in the file; the button that goes ahead says so too.

Either file explains itself at the top, so you can tell them apart months later without opening the settings again — one says no secrets are in it, the other says in capitals that they are.

A file with keys in it has none of the protection SimpleVPN gave them. Anyone who can read it can connect to this VPN as this Mac, and a copy in mail, a shared folder, a repository or a Time Machine backup cannot be recalled. Delete it once the other client has it — and if it does get out, generate a new key pair and register the new public key with your provider.

On a Mac whose settings your organisation has locked, both buttons are unavailable along with the rest of the editor.

Server Address

Required.

The computer this tunnel connects to — a name like ssh.example.com, or an IP address. This is the machine you'd reach with ssh in Terminal; the tunnel signs in to it the same way.

Port

Default: 22.

The port the server's SSH service answers on. Almost every server uses 22; only change it if whoever runs the server told you a different number.

Connect Timeout

Default: system default.

How long to wait while establishing the SSH connection before giving up. Set a short value for a fast, clear failure when a host is unreachable.

Jump Host

Optional.

A stepping-stone computer (a bastion) this connection goes through first: SSH signs in to the jump host, then hops on to the real server from there. Common on locked-down networks where only the bastion is reachable from outside.

The jump host signs in independently of the server — it has its own username, key and password.

Jump hosts aren't supported by SimpleVPN's built-in SSH engine yet. A configuration with one runs through the system's ssh tool instead, so it can't be combined with a pinned host key — the tool has no way to check a pin, and connecting unpinned when you asked for a pin would be worse than refusing.

Jump Host Port

Default: 22.

The port the jump host's SSH service answers on, when it isn't the usual 22.

Jump Host Username

Default: the tunnel's username.

The account to sign in to the jump host with, when it differs from your account on the server itself.

Jump Host Identity File

Optional.

A private key file for the jump host. It can be a different key than the server's — bastions often issue their own.

Sign-In Method

Default: Automatic.

How this tunnel proves who you are. Automatic tries your identity file, then any keys in the SSH agent, then the password — the classic order. Choosing a specific method uses exactly that method, and nothing else is attempted — so what you chose is what actually signs in, and its failure is reported honestly instead of another method quietly succeeding:

  • Password — the saved or typed password only. Keys and the agent are never offered.
  • Key file — the identity file only (other keys on your Mac are not tried). This includes a hardware security key, which asks for a touch.
  • Certificate — the identity file plus its certificate.
  • SSH agent — only keys held by an SSH agent (1Password, Secretive, KeePassXC, ssh-agent). The key never leaves the agent; choose which one with SSH Agent Socket.
  • Kerberos — your organisation's existing Kerberos ticket (the sign-on from Active Directory, or kinit); nothing to type at all. Never tried unless chosen.

The editor greys out the fields a method doesn't use, and says which choice re-enables them.

Username

Default: your Mac account name.

The account name to sign in to the server with.

Identity File

Optional.

A private key file that signs you in without typing anything (e.g. ~/.ssh/id_ed25519). Leave empty to use your default keys, any keys in the SSH agent, or a password. Used by the Automatic, Key file and Certificate sign-in methods.

Hardware security keys. A key created with ssh-keygen -t ed25519-sk (or -t ecdsa-sk) works here too — point this field at the private half, exactly like any other key. That file is only a handle: the signature is made by the device, so connecting waits for you to touch the key (and to enter its PIN if it has one). Plug it in before connecting; a tunnel that seems to hang at sign-in is usually a security key waiting for a touch. Keys held by the SSH agent work as well, in which case the agent — not SimpleVPN — asks for the touch.

Certificate File

Optional.

An OpenSSH certificate — a file ending in -cert.pub — that vouches for your key. Some organisations issue these instead of putting every user's key on every server: the server trusts the organisation's signing authority, and the certificate says your key belongs. Set it alongside the identity file it certifies, and choose the Certificate sign-in method. If you weren't given one, you don't need one.

Signing In With An SSH Agent

An SSH agent holds your keys and signs on their behalf. Choosing it as the sign-in method means SimpleVPN never has a copy of the private key at all: it hands the server's challenge to the agent, the agent signs it, and the key itself stays where it lives. That is strictly safer than pointing us at a key file, and it is the only way to use a key that cannot be copied — one in the Secure Enclave, or on a hardware token.

Anything that speaks the OpenSSH agent protocol works: 1Password, Secretive (keys generated inside this Mac's Secure Enclave), KeePassXC, and macOS's own ssh-agent holding a YubiKey or any ssh-add-ed key. The agent decides whether to sign — so it, not SimpleVPN, is what shows you a Touch ID prompt, an approval sheet, or a request to touch your token.

Which agent gets asked. By default, the one macOS gives every app in your login session — its built-in ssh-agent. Agents that ship with an app listen somewhere else, in their own folder, and the line in a shell startup file that points ssh at them is not read by an app you launch from the Dock. That is what SSH Agent Socket is for, and the editor offers a one-click fill for any agent it can see.

What the row tells you before you connect. The Sign-In section says what the agent is holding right now — “Your SSH agent has 3 keys: …”, “Your SSH agent is running but holds no keys”, “No SSH agent is running” — so choosing this method is a decision rather than a hope. Check Again re-asks after you unlock a vault or start an agent.

When it doesn't work, the reason is named, because the three causes need three different fixes:

  • No agent answered. Nothing is listening where we looked. Start your agent, or set SSH Agent Socket to where it listens. (If the socket was there and has gone, the message says that instead — an agent that has quit leaves its address behind.)
  • The agent holds no keys. It answered, and offered nothing. Unlock the vault, turn the agent on for the key you want to use, or ssh-add a key to the built-in agent.
  • The server refused the keys. The agent offered keys and the server said no to all of them — the message names them. Add the matching public key to your account on the server, or check you're signing in as the right username.

Where it works. Agent sign-in is available to the SSH tunnel kinds that sign in inside SimpleVPN itself — the SOCKS proxy and port-forward modes. The SSH Network Tunnel kind cannot use it: that session is made by SimpleVPN's network extension, which runs outside your login session and so cannot reach your agent. Give that kind a key or a password instead.

Agent forwarding (OpenSSH's ForwardAgent) is deliberately not offered. It only means anything for a remote shell, which a tunnel never opens — and it would let anything running as root on the server use your keys for as long as you stay connected. There is nothing to forward here, so there is no switch for it.

SSH Agent Socket

Default: empty — the agent macOS provides.

Where the agent you want to use is listening (the same idea as OpenSSH's IdentityAgent). Leave it empty and SimpleVPN asks the agent your login session already provides, which is macOS's own.

Set it when your keys live in an app's own agent. The editor lists the ones it finds with a button that fills this in for you; the current paths are:

  • 1Password — ~/Library/Group Containers/2BUA8C4S2C.com.1password/t/agent.sock, after turning on Settings ▸ Developer ▸ Use the SSH agent. Its own guide is the authority: 1password.dev/ssh/get-started/.
  • Secretive — ~/Library/Containers/com.maxgoedjen.Secretive.SecretAgent/Data/socket.ssh. See github.com/maxgoedjen/secretive.
  • KeePassXC — nothing to set: it adds your keys to the agent macOS already runs (turn on Settings ▸ SSH Agent ▸ Enable SSH Agent integration). Leave this field empty. See keepassxc.org/docs/.

Used by the SSH agent and Automatic sign-in methods; the other methods never ask an agent anything, and the row greys out to say so. A full path is required (/ or ~), and macOS limits how long it can be — the row says so rather than failing at connect time.

Password

Optional.

Used when the server asks for a password, and to unlock a protected (passphrase-encrypted) key file. With Remember on it's kept in your login keychain — never in the tunnel's settings file — so you don't retype it.

With the Password sign-in method, any follow-up question the server asks — a verification code, an MFA prompt — is answered with the stored password. Servers that require a fresh code per sign-in aren't suited to a remembered password.

Mode

Default: SOCKS proxy.

How this tunnel carries traffic:

  • SOCKS proxy — one local proxy any app can point at (see Local SOCKS Port). The most flexible mode, and it runs entirely inside SimpleVPN.
  • Port forwards — specific connections only (see Port Forwards). Local (L) and dynamic (D) forwards run entirely inside SimpleVPN too.
  • Network tunnel — a full point-to-point tunnel (ssh -w). It needs root for the network device and “PermitTunnel” on the server, so this build doesn't offer it yet.

Local SOCKS Port

Default: 1080.

Where on this Mac the tunnel offers its proxy: point apps (or the whole Mac, below) at 127.0.0.1 and this port while connected. Two tunnels can't share a port — give each its own.

Route Mac Traffic Through This Proxy

Default: off.

Points the active network service's SOCKS proxy at the tunnel while it's connected (macOS asks for your admin password), and restores the old setting on disconnect. Flipping it while connected applies immediately. Off, only apps you point at the proxy yourself use the tunnel.

Port Forwards

Optional.

Specific connections to carry, one per row:

  • L localPort:host:port — brings a remote service to this Mac: connecting to 127.0.0.1:localPort here reaches host:port on the server's side.
  • D port — a SOCKS proxy on that local port, the same thing SOCKS proxy mode offers, alongside your other forwards.
  • R remotePort:host:port — the reverse: publishes something reachable from this Mac onto the server's side.

While connected, edits apply live — each row shows whether its forward is active — and no reconnect is needed.

Reverse forwards (R) aren't supported by SimpleVPN's built-in SSH engine yet. A tunnel with one runs through the system's ssh tool instead, so it can't be combined with a pinned host key. Local (L) and dynamic (D) forwards have no such limit. Adding a reverse forward to an already-connected tunnel is refused with that reason rather than silently ignored — reconnect and it will be established by the ssh tool.

Host Key Checking

Default: Trust on first use.

How SSH treats the server's identity key: Trust on first use accepts an unknown host once and remembers it (a changed key is always refused — that's the signature of an interception) — the sensible default. Only known hosts refuses anything not already in your known_hosts. Never check disables verification entirely.

“Never check” leaves you open to man-in-the-middle attacks. Use only for throwaway hosts you don't care about.

Pinned Host Key

Optional.

The strictest identity check: accept exactly one server key — the one whose SHA-256 fingerprint you paste here — and nothing else, not even entries in known_hosts. Get the fingerprint from the server's administrator, or from the server itself with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub. Both SHA256:… and bare 64-character hex forms are accepted.

The pin is enforced by SimpleVPN's built-in SSH engine, which checks it before signing in. That covers SOCKS proxy mode and port forwards that use only local (L) and dynamic (D) rows. The system ssh tool has no equivalent check, so a pinned tunnel refuses to run through it and never falls back — meaning a pin can't be combined with a jump host, extra options, a reverse (R) forward, or network tunnel mode. Connect says which of those it was.

Key Exchange

Default: empty — the engine's built-in preference.

Which methods may be used to agree the session's encryption keys, as a comma-separated list in OpenSSH's KexAlgorithms syntax. Leave empty for the built-in choice, which already prefers the post-quantum hybrids (mlkem768x25519-sha256, sntrup761x25519-sha512) when the server supports them — protection against traffic recorded today being decrypted by future quantum computers.

Only set this if an administrator gave you an exact list, or to require post-quantum protection by listing only those methods (the connection then fails against servers that can't do it). A list the server doesn't share any method with simply prevents connecting.

Keepalive

Default: 30 seconds.

Sends a small keepalive at this interval so NAT routers and firewalls don't silently drop an idle tunnel. Lower it on aggressive networks; 0 disables it.

Compression

Default: off.

Compresses the SSH stream. Worth trying on very slow or high-latency links; on fast connections it just adds CPU work for no gain.

Extra Options

Optional.

Raw ssh_config directives, one per line as “Key Value” (e.g. Ciphers aes256-gcm@openssh.com, MACs hmac-sha2-512). An escape hatch for anything this screen doesn't expose. A tunnel using extra options runs through the system ssh tool rather than the built-in engine.

Server Address

Required.

The VPN gateway to connect to — the name or address your administrator gave you, such as vpn.example.com. Every vendor has its own word for this machine (F5 calls it a virtual server, Cisco a headend or concentrator, Palo Alto a portal and a gateway, Juniper a Connect Secure), and they all go in this one field. Give the address only: a username belongs in Username, and a non-standard port in its own field rather than after a colon. A password embedded in the address is refused outright — it would be stored unencrypted and handed to the tool on a command line any program on this Mac can read.

Until this is filled in the VPN still appears in the main window's list, with Connect disabled and a note saying the address is missing — it is never hidden.

Username

Optional — required by password sign-in.

Who you sign in as. Sent by the Password sign-in method together with your password. With a client certificate or single sign-on, the certificate or the identity provider says who you are and this field is not used. Some gateways also want a realm or group alongside it; that has its own field.

Password

Optional — required by password sign-in.

Your password for the VPN, kept in your login keychain when “Remember password” is on and handed to OpenConnect on a private pipe — never on its command line. It is sent only by the Password sign-in method: with Client certificate or single sign-on selected the field is inert, and nothing is transmitted. Whichever method you choose is the one used — no other is quietly attempted.

Client Certificate

Optional — required by certificate sign-in.

A file that identifies you to the gateway instead of a password: a PEM certificate, or a .p12/PKCS#12 bundle holding the certificate and its key together. Choose the Client certificate sign-in method to use it. Under the Password or single-sign-on methods this file is ignored entirely — it is not presented “just in case”, because a certificate offered alongside a password takes over the whole sign-in.

Client Private Key

Optional.

The private key belonging to the client certificate, for the common case where they are two separate files. Leave empty for a .p12 bundle or a PEM file that already contains the key.

Key / PKCS#12 Passphrase

Optional.

The passphrase that decrypts your client key or .p12 file. Stored in your login keychain and used only by certificate sign-in.

Smartcards & Security Keys

SimpleVPN cannot sign in with a certificate held on a smartcard. Not on the SSL VPN kinds, not on OpenVPN, not anywhere. If your gateway will only accept the certificate on a card or a PIV-enabled YubiKey, SimpleVPN is not a client you can use for it today, and the honest thing is to say so on this page rather than let you find out at the end of a setup.

There was an implementation and it was removed. It had never been run against a real card or a real gateway — the machine SimpleVPN is built on has neither — so nobody could say whether it worked. A sign-in method that might silently fail is worse than one that isn't offered: you would have spent your card's PIN retry counter finding out, and on a YubiKey exhausting that counter destroys the key it protects. The option is still in the Sign-in method list so that this page can be found, and choosing it shows the same notice rather than a form.

What does work instead. A certificate in a file — a PEM pair or a .p12 bundle — is fully supported: see Client Certificate. So is single sign-on on the gateways that offer it, which is often how an organisation that issues cards also allows a browser sign-in with the same identity. Ask whoever runs your gateway which of those two is available to you.

If neither is, tell us. Whether this is ever built depends entirely on hearing from people who need it, and what decides it is your situation rather than a vote. Open an issue describing three things: which gateway (AnyConnect, GlobalProtect, FortiGate, F5 APM, Juniper, Pulse, Array), which card or key and the module that reads it, and what your organisation requires — in particular whether it leaves you any other way in. The Tell Us What You Need button on the notice in the editor opens a report with those questions in it and fills in what SimpleVPN already knows about your setup, so you don't have to describe it. Nothing is sent until you have read it. There is no commitment either way.

A verification code SimpleVPN generates — TOTP, HOTP, RSA SecurID — is a separate thing and also not offered: SimpleVPN asks you for the code instead, and a password app that holds codes can fill it in. Holding the seed would mean carrying a secret that generates every future code into the part of SimpleVPN that builds the tunnel, and there is no channel for that. The same notice appears for a VPN that still has one configured, with the same invitation.

A YubiKey that types a code is not affected. That is a different mechanism on the same piece of plastic: the key acts as a keyboard and enters a one-time code, or computes an OATH code that SimpleVPN reads back. It is built, it is supported, and it is documented under Security Keys. What is missing is only the certificate its PIV applet can hold.

The engineering reasons — why the built-in engine cannot do it, and why rebuilding it differently would not have helped — are recorded in Docs/AuthSecPKCS11.md in the source, for anyone who wants them.

Sign-In Browser

Default: the app default (Settings).

Which browser — and, for Chrome/Edge/Firefox, which profile — opens the single-sign-on page, so your passkeys, security key and saved passwords are where you already keep them. Used only by the Single sign-on method, and only for the protocols OpenConnect can browser-sign-in (Cisco AnyConnect, GlobalProtect, Pulse); for the others no browser is opened at all.

Pinned Server Certificate

Optional — but it is the only server-identity check these VPNs have.

Accept exactly one gateway: the one whose certificate matches this fingerprint, and nothing else. Everything else on the Sign-In screen proves who you are; this is the single control that proves the machine answering is the machine you meant to reach. Set it for any gateway with a self-signed or otherwise untrusted certificate — without it, such a gateway is refused outright rather than accepted blindly.

Two forms are accepted, the two OpenConnect itself prints:

  • pin-sha256: followed by 44 characters of base64 ending in = — the hash of the server's public key. The prefix is optional; a bare 44-character pin means this.
  • sha256: followed by 64 hex characters — the certificate's own fingerprint.

Anything else is refused as you type, with the reason under the field, and Connect stays disabled until it is fixed. That is deliberate: a mistyped pin doesn't warn, it fails the connection every time, and it does so complaining about the server's certificate — a very long way from the character that was actually wrong.

A gateway whose certificate comes from a private authority is usually better served by a CA certificate file, which keeps working when the server's certificate is renewed. A pin has to be updated by hand each time.

CA Certificate File

Optional.

A PEM file of certificate authorities to trust for the VPN server, for organisations that issue their server certificate from a private CA. Not needed when the server uses a normal public certificate.

Unlike a pinned certificate, this keeps working when the gateway renews its certificate — the authority stays the same. Prefer it when you were given a CA file.

Perfect Forward Secrecy

Default: off.

Refuses any cipher that doesn't give this session a key of its own, so traffic recorded today can't be decrypted later by someone who obtains the server's long-term key. Every current gateway can do this; the setting exists to require it.

A gateway that can't offer forward secrecy is refused rather than downgraded — that is the point of the setting, but it does mean the connection stops working instead of connecting less safely.

Reported OS

Default: the real OS.

The operating system OpenConnect reports to the server. Some servers run different access policies per OS, or only admit “known” clients — setting this to e.g. mac-intel or win can get you in where the default is rejected.

Disable DTLS

Default: off (DTLS used when available).

SSL VPNs carry data over UDP (DTLS) for speed, falling back to TLS. Turn this on to force TLS — useful when the network blocks the UDP port or DTLS behaves badly, at some cost to throughput.

Skip Host Checker

Default: off.

Many corporate servers run a “host checker” / endpoint-posture script before admitting you. This replaces that step with a no-op so an unmanaged Mac can connect.

A host-checker wrapper (under Advanced) takes precedence: when one is set, that script runs and this toggle does nothing, so the toggle is shown as unavailable and names the wrapper instead of pretending to apply.

Bypassing posture checks may violate your organisation's access policy. Some servers also refuse to connect without it — it cuts both ways.

Run In-Process

Default: off — the openconnect command-line tool runs the VPN.

Carries this VPN with SimpleVPN's own built-in OpenConnect engine, as a full system tunnel, instead of launching the openconnect tool. As a system tunnel it routes the whole Mac by itself, so no SOCKS proxy is opened and Route Mac Traffic Through This Proxy has nothing to do.

The built-in engine deliberately carries only what it can carry exactly: the server, the realm, a pinned certificate, the sign-in browser and your credentials. Any other setting on this screen — a port, a CA file, a client certificate, a host-checker wrapper, a connection proxy, compression, PFS, an MTU, a timeout or extra arguments — sends the connection back to the tool, and the editor says so rather than letting the toggle look effective. Silently dropping one of those would connect with weaker settings than you configured.

Newer than the subprocess path. Check it against your own gateway before relying on it.

Host-Checker Wrapper

Optional.

A script that answers the gateway's endpoint-posture challenge (Cisco's CSD, F5's EPA, GlobalProtect's HIP) so an unmanaged Mac is admitted. Whoever runs the VPN usually supplies it.

It takes precedence over Skip Host Checker: with a wrapper set the script runs and the skip does nothing, so that toggle is shown as unavailable and names this file instead of pretending to apply. Clear this field to go back to skipping the check. If there is no file at the path you typed, the row says so — that is a warning, not a block, because the file may be created before the next connect.

User Group / Path

Optional.

The portal or gateway this sign-in goes to, given as the path part of the address. GlobalProtect uses it to choose between the portal and a specific gateway; Juniper and Pulse expect the URL path of the sign-in realm. Set it only if you were given a path — an address alone reaches the default.

Compression

Default: whatever the gateway proposes.

Whether traffic inside the tunnel may be compressed. Stateful and All ask for it, None refuses it. Leave it on Default unless an administrator names a setting: modern traffic is mostly already compressed, so there is usually nothing to gain, and refusing compression is occasionally a workaround for a gateway that implements it badly.

Disable IPv6 in the Tunnel

Default: off (IPv6 used when the gateway offers it).

Asks the gateway for an IPv4-only tunnel. Worth trying when connections inside the tunnel hang rather than fail — the classic symptom of a gateway that advertises IPv6 it can't actually route. See also IPv6 Leak, which is the opposite problem.

Disable HTTP Keepalive

Default: off (connections are reused).

Opens a fresh connection for each request to the gateway instead of reusing one. A workaround for old proxies and gateways that mishandle a reused connection and stall during sign-in; it costs a little speed and nothing else.

It costs the whole-Mac tunnel. SimpleVPN's built-in engine can't turn HTTP keepalive off, so turning this on runs the VPN with the openconnect tool instead, and that only offers a SOCKS proxy on 127.0.0.1 and the port you set: no interface, no routes and no DNS of its own. The VPN is listed under Local Ports instead of Whole-Mac VPNs, and only apps you point at the proxy use it. Turn it off to get Run In-Process back. The row in the editor says so while it is on.

Reported Hostname

Default: this Mac's real computer name.

Route Mac Traffic Through This Proxy

Default: off.

Allow local network access

Default: off.

Keeps the devices on the network you are physically on — printers, file servers, a NAS, smart-home gear — reachable while the VPN is up. Turn it on if printing or local file shares stop working when you connect.

What leaves the tunnel: traffic to the networks your Mac's own interfaces are on, and to the addresses devices use to find each other (link-local and multicast, which is how AirPlay and Bonjour work). Nothing else. Anyone watching the network you are on can see that traffic, which is why it is off unless you ask for it.

SimpleVPN works out which networks those are when the VPN connects, from the interfaces that are actually up, and never guesses at a wider range — a carve-out wider than the truth would send traffic outside the tunnel that you believe is inside it. Joining a different network later does not move the carve-out; reconnect to pick up the new one. Virtual-machine and container networks are deliberately not included: those have their own offer, which names the guest and says what it will do.

It needs Run In-Process. The openconnect tool carries these VPNs as a SOCKS proxy on a local port and takes no routes at all, so there is no tunnel for a carve-out to make a hole in — the local network was never captured in the first place. With the built-in engine the VPN is a whole-Mac tunnel, and then this is what keeps the printer working. The row says so when the tool is going to run the VPN.

If your organisation manages this Mac and has switched on ForceKeepInsideVPN, the carve-out is refused when the VPN starts, whatever this says. That decision is enforced where the tunnel is actually built, so an older profile cannot get around it.

MTU

Default: auto-detected.

The largest packet size the tunnel carries. Leave empty unless transfers stall, then lower it (e.g. 1300).

Base MTU

Default: auto-detected.

The MTU of the network path underneath the tunnel, which OpenConnect uses to size the tunnel itself. Leave empty; set it only when the link's real MTU can't be detected (some mobile or PPPoE paths).

It costs the whole-Mac tunnel. SimpleVPN's built-in engine can't take a base MTU, so setting it runs the VPN with the openconnect tool instead, and that only offers a SOCKS proxy on 127.0.0.1 and the port you set: no interface, no routes and no DNS of its own. The VPN is listed under Local Ports instead of Whole-Mac VPNs, and only apps you point at the proxy use it. Leave it empty to get Run In-Process back. This is not the same number as MTU, which is carried in-process and is the one to lower when transfers stall. The row in the editor says so while a value is set.

Default: the protocol's own interval.

Default: off.

Use a Shared Secret (PSK)

Default: off — sign in with a username and password.

How you prove who you are to an IKEv2 server: a shared secret that everyone using the VPN has, or your own username and password. Turning this on replaces the username and password fields with a single shared-secret field.

Default: on when a username exists, otherwise off. IPsec (IKEv1) only.

Username

Required by password sign-in.

The account name to sign in to this VPN with. For IPsec it is the personal username the concentrator expects alongside the group secret, and it is only used when XAuth is on.

Password

Required by password sign-in.

Your personal password for this VPN. It is kept in your login keychain and handed to macOS when the tunnel starts. Clearing the field removes the stored password rather than leaving the previous one in place — so deleting it really does mean the next connection won't use it.

Shared Secret

Required by shared-secret sign-in, and by every IPsec connection.

The pre-shared key — also called the group secret or machine secret — which is the same for everyone using this VPN. For IPsec it is always needed; for IKEv2 only when “Use a shared secret” is on. Kept in your login keychain, and cleared from it when you clear the field.

Password (XAuth)

Optional. IPsec (IKEv1) only, when XAuth is on.

The personal password the concentrator asks for on top of the group shared secret. Kept in your login keychain. Unavailable — and not sent — while “Also sign in with a username and password” is off.

Remote Identifier

Default: empty — the server address itself must match.

The identity the server has to prove it has, checked against the name in its certificate. Leave it empty and macOS requires the server address you typed; set it when the server's certificate legitimately names something else (a load-balanced cluster name, for instance) and your administrator tells you what to expect.

This is a check on the server, which is why it sits under Security rather than beside the address it verifies.

Encryption

Default: automatic (macOS negotiates).

The cipher protecting the IKE and data channels. Leave on Automatic and macOS picks a strong one; set a specific value only if your administrator requires it. AES-256-GCM is a solid modern choice.

Integrity / PRF

Default: automatic.

The hash that protects message integrity and derives keys. Automatic suits almost every server; SHA2-256/384/512 are the modern options if you must pin one.

Diffie-Hellman Group

Default: automatic.

The key-exchange group for setting up the secure channel. Higher numbers are stronger; 19–21 and 31 are elliptic-curve (fast and strong). It must match a group the server offers, or the connection fails.

Dead Peer Detection

Default: Automatic — macOS's own rate, a check every 10 minutes.

How aggressively to check the server is still reachable so a dropped tunnel is noticed quickly. Higher reacts faster at the cost of a little extra traffic; Off relies on normal timeouts. Automatic leaves the choice to macOS rather than pinning a rate.

Perfect Forward Secrecy

Default: off.

Runs a fresh key exchange when rekeying the data channel, so compromising one key can't decrypt earlier traffic. Turn on if the server requires PFS.

Key Lifetime

Default: macOS's own — 60 minutes for the sign-in channel, 30 for the data channel.

How long each negotiated key is used before the tunnel quietly agrees a fresh one. Shorter lifetimes limit how much traffic a single stolen key could ever expose, at the cost of a little more renegotiation; longer ones do the opposite. Accepted values are 10 to 1440 minutes (24 hours). Leave it empty unless your administrator gives you a figure — the setting applies to both channels, and a value your server disagrees with shows up as a tunnel that reconnects on a timer.

MOBIKE

Default: on.

MOBIKE lets an IKEv2 tunnel survive your Mac changing networks (Wi-Fi to Ethernet, for instance) without reconnecting. Disable it only if a particular server misbehaves with MOBIKE enabled.

Send All Traffic

Default: off.

Routes all your traffic through the VPN (full tunnel). Off carries only the networks the server routes to you (split tunnel).

Allow Local Network Access

Default: on (when sending all traffic).

Even with everything going through the VPN, keep your local network — printers, file shares, other devices — directly reachable. Turn off for the strictest isolation.

Disconnect on Sleep

Default: off.

Tear the VPN down when the Mac sleeps rather than resuming it on wake. Leave off to have the tunnel come straight back after sleep.

What This Is

One VPN type, two services.

Most VPNs connect you to one server, and everything you reach goes through it. Tailscale is different: it joins your Macs, PCs, phones and servers into a single private network, and they talk to each other directly wherever they happen to be. There is no central server carrying your traffic — which is why the connection details show your own address on the network rather than a server address.

Headscale is the same thing with a server you run yourself: an open-source, Tailscale-compatible coordination server. SimpleVPN uses one engine for both. Choosing “Headscale (self-hosted)” only tells SimpleVPN to ask you for that server’s address instead of using Tailscale’s.

The first time you connect, this Mac has to be added to the network. After that its membership is remembered and connecting is instant.

Service

Default: Tailscale.

Which coordination service this VPN joins: Tailscale’s own, or a Headscale server you run yourself. It is the same engine either way — this choice only decides whether SimpleVPN asks you for a server address.

Changing it after this Mac has joined a network means joining a different network: the membership isn’t transferable, so you sign in again.

Server Address

Headscale only. Tailscale uses its own.

The web address of your self-hosted server, for example https://vpn.example.com. It must start with https:// — the request that adds this Mac to the network carries its identity, and plain http would expose it.

Leave the service set to “Tailscale” and this field disappears, because there is only one address and typing it yourself is only a way to get it wrong.

Name on the Network

Default: your Mac’s name.

What the other machines call this Mac — in their machine lists, and as a name you can connect to directly if “Use this network’s DNS” is on. Change it if your Mac’s name is unhelpful (“MacBook-Pro-3”) or if two machines would otherwise share a name.

Setup Key

Optional.

There are two ways to add this Mac to the network:

Sign in with a browser (leave this field empty). The first time you connect, SimpleVPN opens a sign-in page; you approve this Mac there and the connection completes on its own. This is the normal way, and you only do it once.

Use a setup key. Your network’s admin page can issue a key (it starts with tskey-auth-) that adds a machine without anyone signing in. Useful for a Mac that has to reconnect unattended, or where opening a browser isn’t practical. Paste it here and it is kept in your Keychain, never in the VPN’s settings file.

A setup key is a credential: anyone holding it can add a machine to your network. Prefer a key that is single-use and expires, and remove it from this field once this Mac is signed in — it isn’t needed again.

Use Shared Networks

Default: on.

Some machines on the network offer a whole network they sit on — an office LAN, a home network, a cloud subnet — so the others can reach it. With this on, those networks are reachable through this VPN as well as the individual machines. Turn it off if you only want to reach the machines themselves.

Use This Network’s DNS

Default: on.

Lets you use machine names instead of addresses (fileserver rather than 100.92.4.17), and uses whatever DNS servers your network specifies. If the network only claims certain name suffixes, only those go to it and everything else keeps using your Mac’s normal DNS.

Send Internet Traffic Elsewhere

Default: off.

Normally only traffic to your own machines goes through this VPN; everything else takes its usual route. Turn this on to send all internet traffic through another machine on the network — the way a traditional VPN works. Useful for appearing to be somewhere else, or for using a trusted connection from an untrusted network.

The machine on your network that carries your internet traffic. Default: on.

What This Is

An SSH Network Tunnel turns one SSH connection into a whole VPN. SimpleVPN creates a network interface, sends the traffic you choose into it, and carries each connection over the SSH server as an ordinary forward — the same thing ssh -L does, but set up automatically for every connection instead of one at a time.

Nothing has to be configured on the server. You do not need root there, and you do not need PermitTunnel: if you can log in with SSH and open a forward, this works.

Two things to know before you rely on it:

  • Only TCP travels. SSH has no way to carry UDP, so it cannot be added later — it isn't a missing feature, it's the protocol. Name lookups still work (they are sent over TCP), but QUIC — which Chrome, Safari and many video apps try first — is refused, and those apps fall back to TCP after a short pause. Anything UDP-only (some games, plain WireGuard, most voice and video calling) will not work at all.
  • Speed is one connection's worth. Everything shares a single encrypted SSH connection, encrypted by a single processor core, so the total throughput is roughly what one download would get. It is excellent for reaching things; it is not a way to make many large transfers fast at once.

If you want a local proxy port instead of a whole network interface, use the plain SSH kind — that is the same connection put to a different use.

Server Address

Required.

The SSH server this tunnel connects to — a name like gateway.example.com, or an IP address. Just the address: SimpleVPN adds the ssh:// part, and the login name goes in Username.

Whatever you put here is automatically kept out of the tunnel. It has to be: the tunnel is carried over this connection, so sending it into itself would be a loop.

Port

Default: 22.

The port the server's SSH service answers on. Almost every server uses 22; only change it if whoever runs the server told you a different number.

Username

Default: your Mac account name.

The login name to use on the server. This is saved with the VPN — a login name is not a secret.

Sign-In Method

Default: Password.

How you prove who you are:

  • Password — the account password on the server.
  • Private Key — a private key you paste in, which SimpleVPN keeps in your Keychain (see Private Key).

There is no SSH agent and no Kerberos option here, and there cannot be. This tunnel runs as a system service, outside your login session, so it can reach neither your agent's socket nor your Kerberos ticket. Paste the key instead — SimpleVPN holds it for you. (The plain SSH kind runs in your own session and does offer both.)

Password

Optional — required by password sign-in.

Why pasted rather than a file path: the tunnel runs as a system service and cannot read files in your home folder, so a path to ~/.ssh/id_ed25519 would be a path to nothing. SimpleVPN reads the key once, keeps it in your Keychain, and hands it over in memory at connect.

Optional.

Resolve Names at the Server

Default: off.

Look names up as the SSH server sees them. This is the thing SSH is uniquely good at: the server resolves the name using its own DNS, so internal names that only exist on its network — and resolvers you have no route to at all — just work.

SimpleVPN advertises an address of its own for this and forwards every lookup sent to it over the SSH connection to Server-Side Resolver. You can leave DNS Servers filled in as well; the server-side resolver is tried first.

Server-Side Resolver

Default: 127.0.0.1:53.

The resolver to use at the far end, as the SSH server sees it. 127.0.0.1:53 means "whatever that server itself uses", which is right most of the time. An internal address like 10.0.0.53 works too, as long as the server can reach it.

MTU

Default: 1500.

The size of the largest packet the tunnel interface will carry.

Unlike most VPNs, lowering this almost never fixes anything here. Other tunnels wrap your packets inside their own, so they need room for an extra header; this one doesn't wrap anything — it ends each connection at your Mac and starts a fresh one at the server. There is no outer header to make room for, so if transfers stall the cause is somewhere else.

Host Key Checking

Default: Trust on first use.

How SimpleVPN treats the server's identity key:

  • Trust on first use — a server you haven't met is shown to you once, and remembered after you press Check and Trust This Server. The safe default.
  • Only known hosts — the key must already be in your ~/.ssh/known_hosts. A server that isn't there is refused.
  • Only the pinned key — nothing but the fingerprint in Pinned Host Key is accepted, not even known_hosts. The strictest setting.

A key that has changed is always refused, whichever of these you choose. That is the signature of someone intercepting the connection, and no setting waves it through.

There is no "never check" option, and there will not be one. The tunnel itself runs as a system service with no way to ask you anything, so it accepts exactly one fingerprint and refuses everything else. Deciding which fingerprint that is happens here, in the app, where you can see it.

Pinned Host Key

Optional — required by “Only the pinned key”.

The one server identity this tunnel will accept: the SHA-256 fingerprint of its host key, as 64 hexadecimal characters. A leading SHA256: and colons between bytes are both fine — SimpleVPN reads either.

Check and Trust This Server fills this in for you: it connects, reads the key, and records it. Whoever runs the server can also give you the fingerprint to paste, which is the stronger option because it never depends on the first connection being genuine.

A partial fingerprint is refused rather than accepted loosely. Comparing only the first few characters would let a key that merely starts the same pass, which is no check at all.

Key Exchange

Default: empty — the engine's built-in preference.

Which key-exchange algorithms to offer, in OpenSSH's KexAlgorithms syntax (comma-separated). Leave it empty unless you have been given a specific list: the built-in preference already favours the post-quantum hybrids, which is what you want.

A list the engine can't parse or agree on fails the connection with a clear message rather than quietly using something else.

Keepalive

Default: 30 seconds.

How often to nudge the server so a quiet tunnel isn't dropped by a router or firewall in between. 0 turns it off.

If the connection does drop, SimpleVPN reconnects on its own and keeps trying. While it is reconnecting the tunnel's routes stay in place, so traffic that would have gone through it is refused rather than sent out over your normal connection — a stall you can see, instead of a leak you can't.

What This Is

Every VPN kind has this tab. It changes nothing until you add a rule.

When a VPN connects it pushes settings at your Mac: which networks it carries, which DNS servers to use, sometimes a proxy. Custom Routing is where you edit that push — accept it, ignore parts of it, replace a value, or add one the VPN never offered — per VPN.

Every rule is written against what this VPN last pushed, which SimpleVPN remembers, so the tab works the same whether or not the VPN is connected right now. Each section shows a “Pushed by this VPN” reference list for exactly that reason. Rules that can’t match anything, or can’t change anything, are marked as such rather than left looking effective.

Custom Routing overrides what your VPN administrator configured. Ignoring a pushed route or resolver can take away access you need — or send traffic outside the tunnel that was meant to stay inside it.

Unmatched Routes

Default: Accept.

What happens to the networks this VPN offers that no rule below mentions. Accept keeps them all, and your rules are exceptions. Ignore drops them all, and only what a rule explicitly accepts or replaces is used — an allow-list.

Route Rules

Default: no rules — routes pass through unchanged.

An ordered list that edits the networks this VPN offers. Each rule has an action and one or two networks (in address/length form, or the word default for the “send everything” route):

ActionWhat it does
AcceptKeep this network, whatever the default above says.
IgnoreDrop this network — the VPN won't carry it.
ReplaceCarry a different network in place of this one.
AddCarry a network the VPN never offered.

Changing a rule’s action clears the field the new action doesn’t use, so nothing invisible survives the change. A rule whose networks overlap a pushed route, or another rule, offers a button that draws the overlap for you. Rules with an error in them stay in your draft but are never applied.

The order matters: first match wins

The list is tried from the top down against each network the VPN offers, and the first rule that matches decides. Later rules that also match that network never run. Anything no rule mentions follows Unmatched Routes above. Add rules are the exception: they inject a network the VPN never offered, so they apply wherever they sit in the list.

That makes the order part of what these rules do. Two rules for overlapping networks — say Ignore 10.0.0.0/8 and Replace 10.1.0.0/16 — send traffic to different places depending on which is above the other, so moving one is a change to your routing and not a change to your view of it. Every row therefore shows its position, and SimpleVPN marks a rule that can never match because an earlier one always will.

Three ways to move a rule, all the same change:

  • Drag it by its number — a line shows where it will land, so you can see which rule will win before you let go.
  • The up and down buttons beside each rule. Reachable with Tab alone; the first rule’s up button and the last rule’s down button say why they are unavailable rather than doing nothing.
  • Right-click the rule and choose Move Up or Move Down.

A move is part of your draft exactly like any other edit here: Save keeps it, switching to another tab or closing the editor saves it too, and where the editor offers Revert that undoes it — the same as changing a rule’s action or its network. A move is also its own undo: Move Down puts back what Move Up just did. The same applies to Resolver Rules.

Unmatched Resolvers

Default: Accept.

The same choice as for routes, for the DNS servers this VPN offers: keep the ones no rule mentions, or drop them so only what a rule accepts is used.

Resolver Rules

Default: no rules — resolvers pass through unchanged.

An ordered list that edits the DNS servers this VPN offers, with the same four actions as route rules: accept one, ignore one, replace one with another, or add a server of your own. Values are plain addresses.

The order works exactly as it does for routes — first match wins, and rules move by dragging their number, by the up and down buttons beside them, or from the right-click menu.

Replacing a VPN’s DNS server with a public one means the names inside your organisation stop resolving — and it sends every lookup you make to whoever runs the server you chose.

Ignore All Pushed Search Domains

Default: off.

Drops every search domain this VPN offers. Search domains are what let you type a short name (wiki) and have your Mac complete it to a full one (wiki.example.com).

With this on, the “ignore search domains” list below has nothing left to remove, so it is shown as unavailable rather than pretending to apply.

Search Domains

Optional.

Two comma-separated lists: search domains to add to whatever this VPN offers, and individual ones to leave out. Adding is useful when a VPN forgets a suffix you need; leaving one out is useful when a pushed suffix shadows a name you use locally.

Ignore All Pushed Match Domains

Default: off.

Drops every match domain this VPN offers. Match domains are the name suffixes whose lookups go to this VPN’s DNS servers; everything else keeps using your Mac’s normal ones.

Dropping them all usually means the VPN’s DNS servers stop being consulted for anything — which is a large change disguised as a small switch.

Match Domains

Optional.

Two comma-separated lists: name suffixes to send to this VPN’s DNS servers on top of whatever it offers, and individual ones to leave out. Adding a suffix is how you make one more part of the internal namespace resolve through the VPN; leaving one out keeps a suffix on your Mac’s own DNS.

Proxy

Default: use the proxy this VPN pushes.

Whether to use the proxy this VPN offers, go direct and ignore it, or use a proxy of your own. Choosing Custom reveals the address fields below.

For the OS-native VPN kinds (IKEv2, IPsec) macOS applies the proxy itself and SimpleVPN only observes it — so a pushed proxy’s sign-in can’t be attached there. The tab says so where it matters instead of offering a field that does nothing.

Manual Proxy Address

Optional. Custom mode only.

The proxy to use while connected, as http://host:port, https://host:port or socks5://host:port. Ignored while a PAC URL is set — that wins, so the field is shown as unavailable rather than left editable and inert.

The native VPN configuration has no SOCKS slot, so on those kinds a socks5:// address can’t be applied; the tab says so instead of failing quietly.

PAC URL

Optional. Custom mode only.

The address of a proxy auto-configuration script — a small file, published by whoever runs your network, that decides per-site which proxy to use. It takes precedence over the manual address above.

Proxy Sign-In

Optional.

The username and password the proxy asks for, if it does. Used both for a proxy you configured here and for one this VPN pushed — a push never carries credentials, so if the pushed proxy wants a sign-in this is where it comes from.

The pair is kept in your login keychain; the VPN’s settings only ever carry a reference to it. Clearing both fields deletes the stored secret. Choosing “Ignore (direct)” keeps what you typed but drops the reference, so an unreferenced secret can never reach a connection.

Security Keys — What This Is

A security key — a YubiKey or something like it — can supply this VPN’s verification code, so you never type one. Four different things a key can do, and they are genuinely different:

  • The code the key types. The key pretends to be a keyboard. Touch the gold disc and it types a long code beginning cccc, then presses Return. This is the factory setting on most keys.
  • A verification code stored on the key — the ordinary six- or eight-digit kind, kept on the key instead of on your phone. SimpleVPN asks the key for it using Yubico’s own command-line tool, ykman, which you install yourself.
  • An answer to a challenge. Your VPN sends a challenge, the key answers it, and the answer is the code. The key’s secret never leaves the key.
  • A fixed password stored on the key. Not a one-time code — the same every time. SimpleVPN supports it so that it works rather than being mangled.

Because the key types, the cursor has to be in the right box. A security key types into whatever has keyboard focus, anywhere on the Mac — there is no way for it to aim. So SimpleVPN does not just show you a box and hope: when it is ready for your key it says “Touch your security key now”, puts the cursor in the right box for you, counts down, and gives you a Cancel button.

The Return your key presses will never connect on its own. Your key presses Return after the code, and in a sign-in form Return normally means “connect”. If that fired, SimpleVPN would try to connect the instant the code arrived — possibly before the rest of your sign-in was ready — and a one-time code that fails is gone. So SimpleVPN swallows the Return your key sends. You connect when you are ready, by pressing Return yourself or clicking Connect.

A code is used once and never re-sent. If a connection fails, SimpleVPN clears the code and asks for a fresh touch rather than trying the old one again. Retrying a spent code cannot succeed, and on some systems repeated failures lock the account.

SimpleVPN cannot tell you whether a code is valid. It checks the shape and passes the code on; your VPN’s server (or Yubico’s validation service) decides. If a code is rejected, the usual causes are the wrong key, the wrong account on the key, or a keyboard layout that scrambled it — see below.

Keyboard layouts. The key sends key presses, and your Mac decides which letters they are. The code’s alphabet was chosen to survive the common layouts, but Dvorak and non-Latin layouts scramble it. If the right number of characters arrives but they are the wrong ones, SimpleVPN says so and tells you to switch input source.

What SimpleVPN does not do. It never reads your keyboard. It never asks for Input Monitoring, and it never will — the key types into the box SimpleVPN has focused, so there is nothing to monitor. Detecting that a key is plugged in reads the list of attached devices macOS already publishes, which needs no permission at all.

Use a Security Key

Default: off.

Turn this on and this VPN’s verification code comes from your security key instead of being typed. Only available once this VPN is set to ask for a verification code — a key that supplies a code to a VPN that wants none has nothing to do.

Unavailable when something else already supplies the code: a password app that computes it (1Password, KeePassXC), or a Touch ID-protected sign-in that holds your authenticator’s setup key. Two sources for one code would send the wrong one, so pick whichever you want.

What the Key Supplies

Default: the code my key types.

Which of the four things above your key does for this VPN. The two “typed” kinds need nothing installed. The other two need Yubico’s own command-line tool; SimpleVPN shows the command to install it and never installs it for you.

Where the Code Goes

Default: joined onto the end of my password.

How the code reaches the gateway. Joined onto the end of my password sends your password and the code as one — what most VPN gateways expect, and the usual choice. Sent on its own answers the server’s own prompt and never mixes the code into your password. The code is the whole sign-in sends no password at all.

This choice decides this VPN’s password template (under Verification Code ▸ Advanced) while a security key is in use, so that row becomes unavailable rather than being silently overruled — one control, one meaning. This row is unavailable itself when this VPN’s own configuration asks the server for the code separately; there is then nothing to join.

Account on the Key

Optional — required for a code stored on the key.

Which account on your key holds this VPN’s code, named exactly as your key lists it (usually Issuer:name). Run ykman oath accounts list in Terminal to see them.

The name is passed to Yubico’s tool as an argument; the code comes back privately and never appears on a command line, in a log, or in this VPN’s saved settings. If your key’s code list is protected by a password, SimpleVPN will not pass that password on a command line where other programs could read it — run ykman oath accounts code -r <name> once in Terminal to let Yubico’s tool remember it on this Mac.

Key Slot

Default: Slot 2.

Which of your key’s two slots answers a challenge. Slot 2 is the usual one: slot 1 normally holds the code your key types, and overwriting it is a thing people regret. Slot 2 is reached with a long touch — hold for about three seconds.

This is the same operation a KeePass database uses when it asks for a security key to unlock, so a slot that already works for your password database will work here.

Security Key Serial Number

Default: empty — whichever key is plugged in.

Only needed if you carry more than one key. The serial number is printed on the key, and it is digits only. Leave it empty and SimpleVPN uses whatever is plugged in, which is right for almost everybody.

How Long to Wait for a Touch

Default: 30 seconds.

How long SimpleVPN waits for your touch before giving up (5–120). Long enough to find a key in a bag; short enough that a prompt left open does not sit there all afternoon quietly catching your typing.

Wait for a Touch Automatically

Default: on.

Start waiting for your key as soon as the sign-in is ready, so the cursor is already in the right box when you reach for it. Turn it off to wait until you click — worth doing if you would rather nothing started listening on its own.

Sign-In Sources

A “sign-in source” is where a VPN’s username and password come from when you connect: you type them, SimpleVPN keeps them for you in the Apple keychain, macOS fills them in from Apple Passwords, or a password app hands them over. These settings live in SimpleVPN ▸ Settings ▸ Sign-In Sources and apply to every VPN at once — each VPN then picks one of whatever is on offer.

Two of them need a word of explanation, because they are the reason this pane exists.

SimpleVPN is fussy about which programs it runs. A password app’s command-line tool is about to be asked for a password, so SimpleVPN only starts one from the folders that package managers install into — Homebrew’s, MacPorts’, the system ones, and the per-user folders Python installs use. It deliberately ignores your shell’s search path, because anything that can add a folder to that path could otherwise choose which program gets handed your password. It also refuses any folder that everyone using this Mac can write to, and it refuses that even if you ask for it by name.

But it will still tell you where your tool is. Looking is a different question from running, so SimpleVPN searches much more widely than it will run from: every package manager and version manager it knows about, the folders vendors’ own installers use, the tools that ship inside application bundles, and your search path. That is why you may see “found at …, but SimpleVPN won’t run it from there” — which is the truth, and much more use than being told a tool you can see with your own eyes is not installed. When that happens, paste the path into the tool’s own field: pointing at a copy deliberately is exactly how it is meant to be used.

A path field shows a suggestion in grey when nothing is set. Grey text is a suggestion, not a setting — the field is empty and SimpleVPN is using what it found. Type or paste something and it becomes yours. Use What SimpleVPN Found fills in the suggestion, and Clear empties the field again.

Looking for Password Apps

Default: on.

Lets SimpleVPN find the password apps and command-line tools you already have, so it can offer them as ways to sign in and tell you where they are. It only ever reads this Mac: nothing is sent anywhere, nothing is installed, and nothing of yours is changed. No macOS permission is involved.

Turn it off and SimpleVPN stops looking altogether — no password apps are offered, and none are mentioned. You can still type your sign-in, save it in the Apple keychain, or use Apple Passwords, so nothing becomes unusable. What you lose is every password-app integration, because there is nothing left to find them with.

Your 1Password Accounts

One to begin with — the one you were already using. Add as many as you like.

You can be signed in to more than one 1Password account at a time — a personal one and a work one is the ordinary case — and SimpleVPN has to be told which of them to ask. Each account you set up here gets a name you choose. Each VPN then picks which of them to read when you set its sign-in up: first which account, then which entry inside it.

SimpleVPN cannot work this out on its own, and that is 1Password’s decision rather than a gap here. 1Password has no way to tell another app which accounts you are signed in to, and it refuses a request that does not name one. So this is the one thing about reaching 1Password that has to come from you.

The easiest way to fill it in is to drag. Drag any item out of 1Password onto a VPN’s sign-in and the item brings its account with it — SimpleVPN fills the name in for you, and nothing has to be typed or looked up.

1Password Account

Nothing is set until you set it.

This belongs to whichever of your accounts is selected above.

The name shown at the top of 1Password’s own sidebar. 1Password’s own identifier for the account works here too, and is what a dragged item fills in — it keeps working if you rename the account.

Use Bitwarden

Default: on.

Offers Bitwarden as a way to sign in. SimpleVPN reads one item using bw, Bitwarden’s own command-line tool — the Bitwarden app on its own has nothing SimpleVPN can talk to. Your own self-hosted Bitwarden, and Vaultwarden, work exactly the same way.

The way that works best is Bitwarden’s local service. You unlock your vault once in Terminal and leave bw serve running; the unlock stays inside Bitwarden’s own program, and SimpleVPN reads your item from it over a connection that never leaves this Mac. SimpleVPN never sees your master password, and never sees the key that unlocks your vault.

That is not merely tidier — it is the only way this works without something holding that key. Bitwarden’s command-line tool cannot read your vault at all unless it is given the key from your unlock (Bitwarden calls it BW_SESSION), and SimpleVPN deliberately never keeps one: it is a live key to everything in your vault, so keeping it would be worse than asking. That is also why the tool reports your vault as locked to SimpleVPN even while your own Terminal has it unlocked — that unlock belongs to your Terminal, not to us.

One thing to know about the local service. While it is running it asks nothing of whoever connects to it, so any program on this Mac can read your items from it. That is Bitwarden’s design. Stop it when you have finished, and prefer to start it when you need it.

Off means SimpleVPN neither offers Bitwarden nor mentions it, even if it is installed.

Optional. Empty means 127.0.0.1:8087, which is where bw serve listens unless you tell it otherwise.

Where Bitwarden’s local service is listening, as an address and a port. Set it only if you start the service on a different port (bw serve --port 9000).

It must be an address on this Mac. SimpleVPN refuses anything else and says so, rather than using it: the service asks nothing of whoever connects to it, so a request sent across a network would be a request for your password sent to whatever happened to answer. 127.0.0.1 and localhost are accepted; a machine on your network is not, even if it really is running bw serve.

Use Dashlane

Default: on.

Offers Dashlane as a way to sign in. SimpleVPN reads one entry using dcli, Dashlane’s own command-line tool — the Dashlane app on its own has nothing SimpleVPN can talk to, and there is no other local way in.

Your password is printed to SimpleVPN, never copied to your clipboard. This is worth knowing because it is the opposite of what that tool does by default: run dcli p yourself and it puts the password on the pasteboard, where every program on this Mac can read it. SimpleVPN asks for --output json instead, which prints the entry straight to SimpleVPN and never touches the pasteboard at all. Nothing is left behind for anything else to pick up.

Dashlane does the unlocking, not SimpleVPN. Your Dashlane password goes to Dashlane’s own tool, which keeps the key it needs in this Mac’s keychain where macOS protects it. SimpleVPN never sees your Dashlane password and never changes Dashlane’s own setup.

One-time setup, in Terminal. Run dcli sync. Dashlane asks for your email address, then for a token — by email, or from your authenticator app if you use one — and then for your Dashlane password. That registers this Mac with your Dashlane account once. After that, connecting needs nothing typed.

If you would rather be asked for a fingerprint, run dcli configure user-presence --method biometrics. Dashlane then asks for Touch ID itself, in its own words, before it hands anything over — SimpleVPN only waits for the answer. Turn it off again with --method none.

Two things that can surprise you. Dashlane refreshes its own copy of your vault about once an hour, so a connect now and then takes a moment longer and needs the internet; dcli configure disable-auto-sync true stops that, and you then run dcli sync when you want fresh data. And if you have turned off dcli configure save-master-password, Dashlane asks for your password every single time — which SimpleVPN cannot answer, so it will say Dashlane is locked instead of guessing.

Verification codes: SimpleVPN works one out from the entry when the entry carries one, but it does not promise to — you may still be asked to type a code. That promise has never been watched working against a real Dashlane vault, and SimpleVPN does not make promises it hasn’t seen kept.

Off means SimpleVPN neither offers Dashlane nor mentions it, even if it is installed.

Use a KeePass Database File

Default: on.

Offers a KeePass database file as a way to sign in. SimpleVPN opens the .kdbx file you point it at and reads the entry you name. This is the choice for Strongbox and KeePassium as well as KeePassXC: all three keep their entries in the same kind of database, and none of them has to be running.

SimpleVPN only ever reads your database. It never writes to it, never converts it and never changes anything in it. A password database that goes wrong cannot be repaired, and it is not SimpleVPN’s file.

SimpleVPN does not do the decrypting. The opening is done by keepassxc-cli, the command-line tool that comes inside KeePassXC — the same people who define the format. No part of SimpleVPN decrypts your database.

One thing to know before you choose this. Unlike the other ways of signing in, SimpleVPN does see your database’s password, because a file has nobody to hold it for you. By default nothing is kept: you type it once each time you open SimpleVPN. You can ask macOS to remember it behind Touch ID instead. If KeePassXC is running on this Mac, Use KeePassXC above is the better choice — there the app does the unlocking and SimpleVPN never sees anything.

KeePass Database File

Nothing is chosen until you choose it.

KeePass Key File

Optional. Empty means your database doesn’t use one.

Some databases need a key file as well as a password. If yours does, point SimpleVPN at it here. If it doesn’t, leave this empty.

SimpleVPN never reads the key file itself — it passes its location to KeePassXC’s tool, which does. There is no filter on the file’s name, because a key file may be called anything: KeePassXC writes .keyx, older versions wrote .key, and a hand-made one often has no extension at all.

Use LastPass

Default: on.

Offers LastPass as a way to sign in. SimpleVPN reads one entry using lpass, LastPass’s own command-line tool — the LastPass app on its own has nothing SimpleVPN can talk to.

Your master password never reaches SimpleVPN, and neither does the key it makes. You sign in once in Terminal with lpass login you@example.com. LastPass’s tool then leaves a small helper running in the background holding the key to your vault, and every later read is silent. That helper hands the key to lpass and to nothing else: it checks that whatever asks is the same program it is, and refuses everything else, SimpleVPN included. So there is nothing here for SimpleVPN to store, and nothing for it to ask you for.

This one is best-effort, and it is worth knowing why before you rely on it. LastPass’s tool is the least capable of the ones SimpleVPN reads, and three of its limits are not things this app can work around:

  • It can never give a verification code. There is no field for one anywhere in what the tool hands back, and no command to ask for one. If your VPN needs a code, you type it every time.
  • Its memory expires. The helper quits after an hour by default, and after that SimpleVPN cannot read anything until you sign in again in Terminal. To be asked far less often, put LPASS_AGENT_TIMEOUT=0 in the file ~/.lpass/env — nought means never forget.
  • An entry set to ask for your master password every time cannot be read at all. LastPass calls that “Require Password Reprompt”. SimpleVPN will not ask you for your LastPass master password, so an entry using it is one SimpleVPN says no to rather than one it prompts for. Turn the setting off on that entry, or point the VPN at a different one.

The tool itself also moves slowly, so what works today is what will keep working; nothing new is likely to arrive.

Nothing goes to the clipboard, and SimpleVPN checks. LastPass’s tool has an option that copies a password to the clipboard instead of handing it over, and it can be switched on permanently by a file called ~/.lpass/alias.show — LastPass’s own documentation suggests exactly that. SimpleVPN never asks for it, and there is no way to cancel it once that file says so, so instead SimpleVPN reads that file and refuses to fetch while it would apply, telling you the one line to remove. A VPN password left on the clipboard can be read by anything running on this Mac.

SimpleVPN reads the copy already on this Mac. It never asks LastPass’s servers when you connect, so connecting never waits on the network and never uploads anything. The one consequence: if you change a password in your browser, run lpass sync once so this Mac has the new one.

The entry’s name has to match exactly, including its folders — Work/VPN/GR Lab, not GR Lab. Its numeric id works too, and is worth using when two entries share a name. SimpleVPN deliberately does not use the tool’s loose matching: a search that nearly matches could read a different entry, and reading the wrong sign-in is worse than reading none.

SimpleVPN only ever reads, and only ever the one entry a VPN names. Nothing is added, changed or removed in your vault, and SimpleVPN never signs you in or out.

Off means SimpleVPN neither offers LastPass nor mentions it, even if it is installed.

Use Proton Pass

Default: on.

This is not the same thing as a password store. The two sit next to each other in this list and their tools are called almost the same — Proton’s is pass-cli, the unix password store’s is pass — but they are different products holding different sign-ins. SimpleVPN keeps them completely apart, and setting one up does nothing for the other.

Your Proton plan has to include the tool. It comes with Pass Plus, Pass Family, Pass Professional and the Proton bundles. On a free plan you can install it and watch it start, and Proton will still refuse to sign it in — and because it signs itself back out when that happens, SimpleVPN then sees a Mac that is simply not signed in. That is why both messages mention your plan: nothing on this Mac is broken, and there is nothing here to reinstall.

How signing in works: you run pass-cli login once in Terminal. Proton opens your browser and asks you there — or asks in the terminal, if you use pass-cli login --interactive. Either way Proton does the asking. SimpleVPN never asks for your Proton password, your verification code or your Pass extra password, never stores any of them, and never sets the environment variables Proton’s own documentation warns about.

After that, Proton’s tool keeps its own session on this Mac and SimpleVPN reads just the one item each VPN names. You can lock that session with pass-cli session create-lock; while it is locked SimpleVPN says so and points you at pass-cli session unlock, and never asks for the lock code itself.

Naming an item: two ways, and one of them is safer. Each VPN says which vault and which item, like Work/GR Lab. You can use Proton’s own identifiers for both instead — long strings you can copy out of Proton Pass — and for a VPN you depend on that is worth doing: identifiers keep working when you rename or move things, while names do not. Names are also not unique. Proton’s tool, given a name that matches several items, picks one of them; SimpleVPN will not do that. It stops, tells you how many matched, and asks you to use the identifiers or rename one. Reading the wrong sign-in is worse than not reading one.

A bare item name with no vault is refused for the same reason. Proton’s tool would accept it and search whichever vault it has been told is the default — a setting SimpleVPN cannot see and did not choose — and then take the first match inside it. Two guesses to read a password with. Naming the vault costs one word.

Nothing is written, ever: no item is created, edited, moved or deleted, and your vaults are left exactly as they are. Nothing is put on the clipboard either — Proton’s tool has no clipboard option at all, and a VPN password has no business sitting there waiting for the next paste.

Because a verification code may or may not be on the item, SimpleVPN still asks you for one when this VPN needs one. If Proton hands one over, yours is not needed and nothing is lost by having typed it.

Virtual Machines & Containers — What This Is

Two ways a guest reaches the network, and only one of them can be fixed by routing.

If you run virtual machines or containers on this Mac — Apple’s container, UTM, Docker Desktop, Parallels, VMware Fusion, VirtualBox, OrbStack, QEMU — then a VPN that carries all of your traffic can cut them off. These settings live in SimpleVPN ▸ Settings ▸ General ▸ Privacy and let SimpleVPN notice that before it happens, so it can tell you rather than leaving you to work out why a container stopped resolving names the moment you connected.

The important thing to understand first is that there are two kinds of guest networking, and they need opposite fixes. Which kind you have is not a matter of taste; it is decided by the product, and sometimes by the individual virtual machine.

Guests on a network of their own. Apple Containers, UTM in Shared, Bridged or Host mode, VMware Fusion, Parallels Desktop, VirtualBox and OrbStack all give their guests a real subnet behind a real interface on this Mac — something like 192.168.64.0/24. A tunnel that captures that subnet takes the guests’ traffic with it and they go quiet. For these, keeping the subnet out of the tunnel is the fix, and it is a fix that genuinely works.

Guests with no network of their own. Docker Desktop, and QEMU or UTM in Emulated mode, do something quite different: a program on this Mac translates the guest’s traffic and sends it out as ordinary traffic of its own. There is no interface, there is no subnet, and there is therefore nothing to keep out of the tunnel. Routing settings cannot help these, and SimpleVPN will not pretend otherwise by offering you a routing change that would do nothing. When one of these breaks under a VPN, the two things that actually fix it are the guest’s MTU — lower it to at or below the tunnel’s, see Large transfers stall — and the guest’s DNS, which has to point at a resolver the guest can still reach.

UTM and plain QEMU are in both lists because they support both, chosen per virtual machine. So “UTM is installed” does not decide anything: SimpleVPN reads each machine’s own setting to know which kind it is.

Keeping a subnet out of the tunnel is a split-tunnel decision: traffic to that subnet leaves the VPN and goes over your ordinary connection instead. That is exactly what a guest network needs, and it is still a hole in a full tunnel. SimpleVPN never does it silently and has no setting that would — it tells you, and you decide, per VPN, and the change appears in that VPN’s own list of networks kept out where you can see and undo it.

Look for Virtual Machines on This Mac

Default: on.

Lets SimpleVPN find the virtualization products installed on this Mac, the guest networks that are live right now, and the names of the virtual machines and containers themselves — so it can show them on the Routes map and warn you before a VPN captures them.

It only ever reads, and it only ever reads this Mac. Three things: files where a product’s own installer puts them; the settings files your virtualization apps write for each virtual machine, which is where a name lives; and the list of network interfaces that any program on this Mac may read. Nothing is executed — not docker, not container, not ifconfig, not even a --version. No virtualization daemon is started or woken, no virtual machine is launched, nothing is sent anywhere, and nothing of yours is written or changed. No macOS permission is involved.

Names stay on this Mac. A subnet like 192.168.64.0/24 says nothing about anybody; a virtual machine called client‑acme‑prod can say who you work for. So names are shown to you in the app and are deliberately left out of a problem report, which is a thing you send — the report carries how many guests were found and how they were wired, which is what is actually needed to diagnose routing.

Docker’s and Podman’s containers cannot be named here, and that is on purpose. Their names live inside a running daemon rather than in a file, and reaching them would mean asking that daemon a question — a different thing entirely from reading a settings file your own tools wrote, and one this app does not do. You will see the guest network, not the container names.

“Installed” and “running on a subnet right now” are different questions, and SimpleVPN answers them separately rather than blurring them. A guest subnet only comes into existence when a guest boots, so with nothing running there is no network to name — not even from the product’s own saved settings, which record that it uses NAT without saying which addresses it will use. A machine with three virtualization products installed and none of them running therefore has no guest networks, and that is the honest answer rather than a gap.

Off means SimpleVPN never looks and never warns. Nothing else changes: your virtual machines and containers carry on exactly as before, and a VPN connects exactly as before — you simply find out the hard way when a tunnel swallows a guest network. Turning it off also empties this part of a problem report you choose to send.

Warn Before a VPN Captures Them

Default: on.

When you connect a VPN that would swallow a guest network that is live, SimpleVPN says so — naming the interface, the subnet and, where it honestly can, which product it belongs to — and offers to keep that subnet out of the tunnel.

SimpleVPN never changes routing on its own. The offer is an offer: accept it and the subnet joins that one VPN’s list of networks kept out, where it stays visible and removable. Decline it and nothing is touched. There is deliberately no setting that would do this automatically for every VPN, because sending traffic outside a tunnel is not a decision to make on somebody’s behalf.

The offer only appears where it could work. For a product whose guests have no network of their own there is no subnet to keep out, so instead of a routing offer you are told the two things that do help — the guest’s MTU and the guest’s DNS. A routing change offered there would look like a fix and be none.

Off means SimpleVPN keeps looking but stops speaking up: the facts are still available in a problem report and in the connection details, and no banner appears when you connect. Turn off Look for Virtual Machines on This Mac instead if you would rather it did not look at all.

Seeing Your Guests on the Routes Map

In Window ▸ Routes, in the first column, whenever something is running.

The Routes map draws where this Mac’s traffic goes. Virtual machines and containers appear in it as cards of their own, to the left of This Mac — which is where they are: a guest sends a packet into this Mac, and this Mac then decides whether it leaves by a VPN or by your ordinary connection, exactly as it does for any app. Cards appear and disappear as guests start and stop; you never have to reopen the window.

Each card names the guest network, its subnet, how many guests are on it, and which of the three arrangements it is, because they do not route the same way:

  • Shared network — the guests sit behind this Mac and share its connection, so their traffic goes wherever this Mac’s does. This is what Apple’s container and UTM’s Shared mode give you.
  • Bridged network — the guests are on the same network as this Mac, with addresses of their own from it. This Mac is not in the way, so no VPN here can change where their traffic goes, and SimpleVPN offers no control that pretends otherwise.
  • Host-only network — the guests can reach this Mac and each other and nothing else. There is no way out for a VPN to take away; the only thing at stake is whether this Mac can still reach them. Some products call this a private or internal network.

“SimpleVPN cannot tell” is a fourth answer, and you will see it. Telling a shared network from a host-only one means reading this Mac’s packet filter, and macOS does not let an app do that without administrator access — which SimpleVPN does not take. Where the product writes the answer down somewhere readable, the card says so and says where it read it. Where it does not, the card says it does not know, rather than assuming.

Which Guests, By Name

Only where SimpleVPN can prove which network a guest is on.

A card says “2 running: postgres, redis” rather than “2 guests running” wherever it honestly can, because a name is something you can act on and a count is not. Click the card and every name is listed with the reason SimpleVPN believes it is on that network — there is no confidence score, because a percentage just invites you to round it up. There are two reasons it can ever give:

  • Its hardware address is on that interface right now. UTM, Parallels, VMware Fusion and VirtualBox each record the address their machine will use; macOS knows which interface an address is behind. A match is proof.
  • Its own settings name a network, and there is only one it could be. Apple’s container records which of its networks each container is on. If exactly one guest network is live, nothing else is possible.

Where neither holds, the guest is listed under “Also on this Mac” instead of being placed on a network — with the reason, which is usually either “there is more than one network it could be” or “nothing on any network is using the address recorded for it, so it does not appear to be running”. This is deliberate and it is the whole discipline of the feature: a guest shown on the wrong network is worse than a guest shown with no network at all, because you would then make a routing decision about the wrong one and nothing on screen would tell you.

A name does not mean a guest is running. Your virtual machines’ settings are on disk whether or not they are switched on, so the map distinguishes three things: running here (on one of this Mac’s guest networks), running on your network (bridged — up, but on your LAN, where a VPN here cannot reach it), and not running.

The line joining a guest card to This Mac carries the answer to the question the map exists for: through a VPN, or around it. It names the VPN, and it says “around some of” when you have more than one and they disagree — a state nobody chooses on purpose and one you cannot otherwise see.

Through the VPN, or Around It

Nothing changes until you press the button. Guest traffic goes through the VPN today, and stays that way.

Click a guest card and it offers one action: Keep Reachable Outside the VPN, or, if you already have, Send Through the VPN. It is the same kept-direct route you could add by hand in that VPN’s own settings — it appears there, and you can see and remove it there — not a second, hidden mechanism.

Two different journeys, and this changes one of them. Keeping a guest network direct changes what this Mac sends to your guests: traffic to that subnet leaves outside the VPN, over your ordinary connection, so the VPN neither carries nor protects it. It does not change how the guests themselves reach the internet — that follows this Mac’s own way out, whichever way this is set, and the card says which interface that is. Anyone who tells you a routing toggle puts your containers outside a tunnel is describing something else.

Guests on the Traffic Graph

Their own throughput, by name. What went through a VPN is not measurable and is not drawn.

The traffic graph (in a connection’s details) plots throughput per network connection, and your guests are in the legend alongside your VPNs — under their names where SimpleVPN can attach one, as “A guest on vmenet0” where it cannot. They are off by default like everything that is not one of your VPNs; switch one on in the legend.

This is a real measurement, not a share-out. Every packet a guest sends or receives crosses its own virtual cable into this Mac, and macOS counts them, so “this container is moving 4 MB/s right now” is a fact.

What the graph cannot tell you is how much of that went through a VPN, and it does not pretend to. Once a guest’s traffic leaves this Mac it has been rewritten to look like this Mac’s own, and nothing distinguishes a container’s packet from your browser’s. A guest’s line is therefore labelled as its traffic with this Mac and never as traffic through a particular VPN. A chart that split tunnel traffic up between your containers would be inventing the split.

One consequence worth knowing: with several guests on one network, SimpleVPN can usually name the network but not always match each guest to its own line, because nothing on disk records which virtual cable a guest was given. Where it cannot, the lines keep their own names rather than being labelled with somebody’s container at random.

When there is no choice, the card says why instead of showing a dead switch: no VPN is carrying it; the guests are bridged and this Mac does not decide; the VPN is a kind whose routes macOS owns; or your organisation has locked traffic inside the VPN. That last one wins over anything already stored — under a managed keep everything inside the VPN policy the card reads “through the VPN” even if a kept-direct route is saved, because that is what will actually happen when the tunnel is built.
